## 2. 下单事务 T1

```text
验证请求格式、地址、支付方式
  → 锁定当前账户行，查询 (user_id, request_id)
  → 已存在：校验 request_hash，返回原订单
  → 未存在：按购物项 ID 顺序加锁并检查归属、数量
  → 按商品 ID 顺序条件增加 frozen
  → 保存订单、OrderItem 快照及原始 expires_at
  → 删除本次结算购物项
  → 写库存／购物车失效任务与 ORDER_TIMEOUT 事件
  → 一起提交
```

同一用户的并发结算在账户行串行化；不同用户竞争同商品时，在库存行串行化。唯一约束是数据库最后一道防线。任何商品缺货或后续写入失败，都回滚整个 T1，不做 Redis 加减补偿。

`request_hash` 当前覆盖排序后的购物项 ID、收货字段和标准化支付方式，不是所有数据库内容的摘要；客户端 discount 不参与授权和计价。订单确认后的交易事实来自快照。重复请求返回原单，不重新计算商品价格。

[StockpileRepository](../../tomatoMall-backend/src/main/java/com/example/tomatomall/repository/StockpileRepository.java) 的 SQL 语义为：

```sql
-- 创建预占：实际实现为 JPQL，检查影响行数必须为 1
UPDATE stockpiles SET frozen = frozen + :q
WHERE product_id = :id AND :q > 0 AND amount - frozen >= :q;

-- 支付：同一个订单事务内执行
UPDATE stockpiles SET amount = amount - :q, frozen = frozen - :q
WHERE product_id = :id AND :q > 0 AND frozen >= :q AND amount >= :q;

-- 取消／超时：只释放该单的预占
UPDATE stockpiles SET frozen = frozen - :q
WHERE product_id = :id AND :q > 0 AND frozen >= :q;
```

这些 SQL 本身不识别某一笔订单。防止重复扣减还依赖订单行锁和合法状态判断，二者缺一不可。

## 3. 支付与关闭的事务边界

### 支付通知 T2

Controller 验签、核对应用和商户后进入事务：锁订单 → 校验金额／交易号 → 检查状态 → 根据快照消耗预占 → SUCCESS 与缓存失效事件一起提交。

重复 SUCCESS 通知不再改库存。已关闭订单收到有效付款证明时，只记录交易号及异常，不擅自重新占用已释放库存。`payment_incident` 不是已经完成退款的证据。

### 关闭：T3 → 外部调用 → T4

```text
T3：锁订单，确认到期／取消请求，记录 CLOSING、next_check_at，提交
       ↓ 数据库事务已结束
是否发起过支付？
  否：直接进入 T4
  是：调用支付渠道查询；待付款时尝试渠道关单
       ├─已支付：进入 T2
       ├─确认关闭：进入 T4
       └─未知／异常：保留 CLOSING，由持久任务重试
       ↓
T4：重新锁订单，仅 CLOSING 可释放库存并转 TIMEOUT／CANCELLED
```

`OrderTimeoutHandler` 本身没有大事务；它通过另一个 Spring Bean 调用事务方法，外部查单不持有数据库订单锁。即使 T3 与 T4 之间收到支付回调，T4 也会重新检查状态。

当前多实例或重复消息可能重复执行外部查单：`next_check_at` 是补偿扫描的到期字段，不是严格的独占任务租约。数据库最终库存变更仍受订单锁保护。外部请求合并、关单任务专属租约可作为后续优化，不能说已经实现。

## 4. Outbox 的领取和确认

[OutboxEvent](../../tomatoMall-backend/src/main/java/com/example/tomatomall/po/OutboxEvent.java) 保存事件 ID、业务 ID、kind、deliverAt、nextAttemptAt、sent、attempts、leaseToken、leaseUntil 和 lastError。

1. 默认每秒查最多 50 条候选事件。
2. 短事务锁事件行，再次确认未发送且租约已空闲／过期；生成 token，租约 60 秒，attempts 加一。
3. 提交领取事务，再发送 MQ 或调用 Redis。
4. 短事务锁事件，只有 token 仍匹配时才能标记成功或安排重试。
5. 失败退避：`min(300000, 1000 * 2^min(attempts,8))` 毫秒。

注意实际公式的最大值是 **256 秒**：指数先在 8 截断，虽然代码外层还写了 300 秒上限。第一轮失败后等待 2 秒。解释代码时不要说当前会逐渐达到精确 5 分钟。

旧 worker 超过租约后仍可能把消息发出去；token 防止它确认新 worker 的领取记录，不能撤回它已经发生的外部发送。业务幂等仍然必要。

## 5. 超时字段和配置

| 配置／字段 | 当前值／用途 |
| --- | --- |
| `TIMEOUT_MS` | 30 分钟，当前是服务代码常量 |
| `expires_at` | 原始业务截止时间，MQ 重发不修改它 |
| `next_check_at` | 初始等于截止时间，进入关闭流程后安排下一次检查 |
| `orders.timeout.scan-ms` | 默认 60000；每批最多 100 单 |
| `orders.outbox.poll-ms` | 默认 1000；每批最多 50 个候选事件 |
| `orders.mq.reconnect-ms` | 默认 10000 |
| 消息 schema | `version=1,eventId,orderId,expiresAt` |
| 终态来源 | 以数据库订单状态和渠道结果为准，不信任消息负载决定关单 |

四线程调度池降低单个外部调用阻塞所有任务的风险，但不代表所有外部请求都已限流、隔离或有生产容量保证。
