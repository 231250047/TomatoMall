# 普通订单与单条超时消息链路：实施和验证

日期：2026-09-16。范围：订单正确性 → RocketMQ 超时 → 故障验证。本轮不扩展商品索引 MQ、秒杀或 Agent。

## 1. 已修改的业务行为

| 场景 | 实现 | 主要文件 |
| --- | --- | --- |
| 下单 | 校验本人购物项、数量、在售状态；多商品按 ID 排序，以 `amount-frozen >= quantity` 条件预占 | `OrderServiceImpl`、`StockpileRepository` |
| 原子性 | 预占、订单、商品快照、移除本次购物项、Outbox 同一事务提交；任一步失败全部回滚 | `OrderServiceImpl.createOrder` |
| 幂等 | 必填 `requestId`，唯一 `(user_id,request_id)`；同一买家的下单用账户行锁串行化，重复请求返回原单；参数摘要不同则拒绝 | `CheckoutVO`、前端 `OrderPage.vue` |
| 计价 | 只读取数据库商品价格，保存快照；现有满 300 减 50／满 200 减 30／满 50 减 5，由服务端自动选择；前端 discount 不授权折扣 | `OrderServiceImpl` |
| 支付 | 验签、核对 app_id／seller_id；事务内核对金额和交易号，按订单快照 `amount-=q,frozen-=q`；重复回调不重复扣减 | `OrderController`、`OrderServiceImpl` |
| 支付入口 | 校验归属、PENDING 和截止时间；生成表单前先记录支付尝试；表单附原始绝对截止时间；生成失败不删订单 | `AliPayServiceImpl` |
| 取消／超时 | 行锁转 CLOSING；事务外查询和关闭渠道交易；确认未支付可关闭后，同事务转终态并仅减少 frozen | `OrderTimeoutHandler` |
| 支付结果未知 | 保留预占，记录 next_check_at；数据库每分钟重试；第 10 次起记录 payment_incident，继续可恢复重试 | `prepareTimeout`、`OrderTimeoutTask` |
| 迟到支付 | 已释放库存的订单不复活；保存交易号及 PAID_AFTER_CLOSE 异常，进入核对／退款处置 | `updateOrderStatus` |
| HTTP 安全 | 删除免验签 test-notify；浏览器 returnUrl 只跳转；详情、支付、取消、隐藏及购买历史校验归属 | `OrderController` |
| 删除 | 终态订单只隐藏；待支付／关单中拒绝删除，取消通过独立接口处理 | `POST /api/orders/{id}/cancel`、`DELETE /api/orders/{id}` |
| 管理库存 | 条件更新总量，不允许低于 frozen；商品删除改为下架以保留预占和历史引用 | `ProductServiceImpl` |
| Redis | 展示缓存，库存值 30 秒 TTL；下单不调用 DECR／INCR；失效任务随库存事务入 Outbox，失败重试 | `StockCacheServiceImpl`、`OutboxWorker` |

`amount` 表示尚未售出的总库存，`frozen` 表示未完成订单预占；可售为二者之差。支付、关单和取消均锁同一订单行，库存和订单终态一起提交。

### 状态转移

```text
PENDING ──有效支付通知──────────────→ SUCCESS
   │
   └─到期／主动取消→ CLOSING ──查到已支付→ SUCCESS
                       │
                       ├─确认未支付且关闭成功→ TIMEOUT / CANCELLED
                       └─结果未知→ 保留库存 + 持久化重试

TIMEOUT / CANCELLED + 迟到的有效支付 → 保持原状态 + payment_incident
SUCCESS / TIMEOUT / CANCELLED / FAILED → 可隐藏，仍保留交易和快照
```

前端支付按钮只在 PENDING 展示；后端再次校验 deadline。CLOSING 提示核对中。结算成功立即消费所选购物项，后续取消不会自动重新加回购物车；重试原 requestId 不依赖购物项是否仍存在。

## 2. 唯一的 MQ 链路

```text
下单事务 → Outbox ORDER_TIMEOUT（原始 expires_at）
  → worker 短事务领取 60 秒租约
  → 事务外同步发送 RocketMQ DELAY 消息
  → Broker 确认后短事务标记 sent
  → 到期消费 → OrderTimeoutHandler → 数据库事务完成 → ACK

消息丢失／消费不可用／关单结果未知 → 数据库补偿扫描 → 同一个 Handler
```

- Java gRPC SDK：`rocketmq-client-java:5.0.7`，本轮 Broker：`5.3.2`。
- Topic：`order-timeout`，必须显式创建为 `DELAY`。默认消费组 `order-timeout-consumer`。
- 消息：`{version:1,eventId,orderId,expiresAt}`，不携带地址、金额或身份凭据。
- 发送重试沿用 eventId 和绝对 deadline；已过期的 deadline 不重新增加 30 分钟。
- Outbox 租约过期可被其他实例领取；完成时比较 leaseToken，旧 worker 不能确认新 worker 的任务。
- 发送失败指数退避，当前公式实际封顶 256 秒（另设 300 秒上限）；失败原因类型和次数落库。异常未吞成成功。
- 发送成功但落库前崩溃可能重复投递。消费者依赖订单状态和数据库锁幂等，不宣称 MQ exactly-once。
- UNKNOWN 在数据库持久交接重试后可 ACK；业务事务失败则返回 FAILURE，消费组按 Broker 策略重试／死信。
- `STOCK_INVALIDATE`、`CART_INVALIDATE` 由同一 worker 直接执行 Redis 删除，本轮不建第二个 Topic。
- 四线程调度器避免单个 MQ 连接重试占住唯一线程，使数据库补偿得不到运行机会。

官方依据：[RocketMQ 延时消息](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)、[官方部署及 SDK 示例](https://rocketmq.apache.org/docs/quickStart/02quickstartWithDocker/)。

## 3. 数据迁移：先核对旧订单

新增字段和 Outbox 是不兼容的数据库改动，不能仅替换 JAR。

1. 备份数据库，在副本上验证；停止旧版本的下单、支付回调和超时任务写入。
2. 导出旧 PENDING 订单、订单快照、Redis ZSet 和库存，逐笔向支付渠道核对。旧版本使用 Redis 预占且购物车可变，不能用“当前购物车”补造历史快照。
3. 正确结清／关闭旧活动订单并核对总库存。缺失快照或支付结果未知的旧单需要人工处理，不做批量猜测性解冻。
4. 如果使用仓库早期 SQL dump，先检查 `V0_legacy_entity_columns.sql` 是否适用；该 dump 还可能落后于其他实体，不把它当成最新完整建库脚本。
5. 执行 `tomatoMall-backend/db/migration/V1_order_correctness.sql`。它在存在活动旧单、非零 frozen 或负库存时主动失败。MySQL DDL 不是整体可回滚事务；脚本只运行一次，部分失败后检查 schema，不能盲目重跑。
6. 将 JPA 配置改为 `ddl-auto: validate`，部署新代码；旧 ZSet 已不作为执行依据。确认旧单已处理完后，按备份策略清理旧队列。
7. 执行 `tomatoMall-backend/db/order-health.sql`，核对活动订单快照合计与 frozen、Outbox 积压和支付异常。

不提供自动回滚到旧库存算法的脚本：新订单的数据库预占与旧 Redis 模型不兼容。需要回退时先停止写入并逐单核对。

## 4. 本地启动与验证命令

### 环境

- 后端 Java 17；本机 Maven 默认 Java 26，本轮显式使用 Microsoft OpenJDK 17.0.20。
- 前端 Node 22；本机默认 Node 16，不满足现有 Vite 构建环境。
- 使用 `application-example.yml` 创建被忽略的本地配置，填环境变量。示例已去除内嵌密钥；需额外配置 `ALIPAY_SELLER_ID`。
- 当前机器没有 Docker；本轮数据库与 Broker 验证使用临时独立进程，不连接原项目数据库。

```bash
# 在 tomatoMall-backend 中，JAVA_HOME 指向 Java 17
mvn -B -ntp clean test
mvn -B -ntp -DskipTests package

# 只能使用可以销毁的独立测试库！测试会 create-drop 表。
mvn -B -ntp -Dtest=OrderTransactionTest \
  '-Dorders.test.jdbc-url=jdbc:mysql://127.0.0.1:33077/tomatomall_order_test?serverTimezone=UTC' \
  -Dorders.test.db-user=root test

# 在 tomatoMall-frontend 中，使用 Node 22
npm ci
npm run build
```

安装 Docker 后可从仓库根目录运行：

```bash
docker compose -f compose.orders.yml up -d namesrv broker
docker compose -f compose.orders.yml exec broker sh mqadmin updateTopic \
  -n namesrv:9876 -c DefaultCluster -t order-timeout -a +message.type=DELAY
docker compose -f compose.orders.yml exec broker sh mqadmin updateSubGroup \
  -n namesrv:9876 -c DefaultCluster -g order-timeout-consumer
docker compose -f compose.orders.yml exec broker sh mqadmin updateSubGroup \
  -n namesrv:9876 -c DefaultCluster -g order-timeout-it

# 后端目录：真实 Broker 测试，普通 mvn test 不自动运行 *IT。
mvn -B -ntp -Dtest=RocketMqTimeoutIT -Dorders.test.mq-endpoints=localhost:8081 test
```

Compose 仅作本地开发示例；本轮不提供生产高可用、安全认证或云部署。Broker gRPC 使用 8081，避免与后端 8080 冲突；单节点同步刷盘不等于多副本高可用。

## 5. 分阶段验证记录

### A：先修正订单和库存

- 已先复现旧代码缺陷：支付金额不符未拒绝；下单后数据库 frozen 仍为 0；多商品缺货未触发数据库事务回滚。
- 测试先失败后改代码。H2 测试验证真实 Spring 事务／JPA；外部缓存、支付网关和消息发送器用可控替身制造故障。
- MySQL 8.0.46 使用独立数据目录和 33077 端口，验证真实 InnoDB 行锁与条件更新。

| 用例 | 断言 |
| --- | --- |
| 12 买家并发争抢 5 件 | 正好 5 个订单成功；frozen=5，无负数 |
| 同一 requestId 并发重试 | 返回同一订单；只预占一次 |
| 第二商品不足 | 首件预占、订单整体回滚 |
| 订单金额超出数据库字段范围 | 插入失败，库存、购物项和 Outbox 全回滚 |
| 其他用户购物项／取消 | 拒绝，不改变库存 |
| 支付重复与快照 | 只消耗该单数量，不清空其他订单 frozen |
| 提前／重复超时 | 提前不关闭，重复不多释放 |
| 支付与超时同时到达 | 只有一个库存终态；迟到款有异常记录 |
| 主动取消并重试 | CANCELLED，解冻一次 |
| 支付结果未知后恢复 | CLOSING 保留预占；持久扫描重试后完成 |
| 通知丢失但查单已付 | 补记 SUCCESS，扣库存一次 |
| 已关单收到已付通知 | 不重新扣库存，记录 PAID_AFTER_CLOSE |
| 库存不变量被破坏 | 支付事务回滚，不用归零掩盖错误 |
| 伪造返回页／免验签通知 | 不改变订单状态 |

### B：再接入超时与故障恢复

| 故障 | 验证点 |
| --- | --- |
| Broker 已接收但生产者确认丢失 | 同 eventId、同 deadline 重试；不重复预占 |

## 6. 剩余验收边界

- **支付宝沙箱端到端未执行**：验签商户字段、查询／关单竞争、绝对截止时间需用真实沙箱账户再验收。
- 已生成支付表单但用户未打开时，渠道可能返回 TRADE_NOT_EXIST。当前保守视为 UNKNOWN，不因“查不到”就释放；持续重试并记录异常，需要运营核对。这是安全优先的明确限制，不能宣传为无需人工介入的完整支付对账系统。
- `payment_incident` 和只读巡检 SQL 已有；自动退款、告警通知、后台异常处理界面本轮不实现。不得直接改订单状态绕过渠道核对。
- Broker 单节点强杀重启已实测；Redis 真实重启、死信重放运维、生产多副本容灾及容量压测尚未实测。
- Outbox 历史清理暂不自动执行；按业务重放窗口制定保留策略后再加入清理任务。
- 旧源文件有截断的 UTF-8 字节，编译会报编码诊断。已将 31 份未触及业务逻辑的旧 Java 文件规范为 UTF-8，保留 javac 原先解释的替换字符；没有猜测性改写无法恢复的原文。
