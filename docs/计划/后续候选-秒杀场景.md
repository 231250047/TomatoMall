## 1. 场景与启动条件

候选业务：在规定时间销售一批限量图书，活动库存、活动价格和每人限购数量由服务端配置。大量用户同时提交抢购请求，系统快速返回缺货、重复请求或处理中；只有持久化订单成功后才允许进入支付。

首版若实施，限定为单活动、单商品、每次购买一本。普通购物车多商品结算沿用阶段 A 的同步事务，不混入秒杀的异步流程。

满足以下条件后，再决定是否排期：

- [ ] 普通订单的权限、金额、库存预占、支付、取消、超时及幂等已通过阶段 A 验收。
- [ ] 已有可重复的普通下单压测基线，记录热点库存行锁等待、数据库连接占用及 p95/p99 延迟。
- [ ] 秋招主线有剩余时间，或者基线实测已出现需要解决的热点写入瓶颈。
- [ ] 能投入时间验证消息丢失、进程重启、重复消费和补偿竞争，不只完成成功路径。

## 2. 为什么需要独立的秒杀链路

普通下单使用 MySQL 条件更新和本地事务保证订单与库存正确，但单个热门商品仍会出现同一库存行的串行更新。增加应用实例或按商品 ID 分库分表，不能拆开同一商品的单行竞争。

秒杀方案分三个层次解决问题：入口限流和去重减少无效请求；Redis 资格预占减少进入数据库的请求；队列限制数据库的处理并发并吸收短时峰值。队列本身不会消除单行写入上限；若持续流入快于消费速度，仍须拒绝或暂停受理。

库存分桶作为进一步优化，只有前面方案实测仍不足时才考虑。

## 3. 候选架构

```text
用户提交 requestId
    → 登录、活动时间、限购、限流校验
    → Redis 原子检查资格并记录 reservationId
    → 可靠投递任务
    → 返回受理结果，前端查询处理状态
    → 消费者按受控并发执行 MySQL 事务
        → 校验活动额度
        → 创建唯一订单与商品快照
        → 持久化库存预占和处理结果
    → 返回订单或明确失败结果
    → 复用普通支付、取消、超时规则
```

“已受理”只表示请求进入处理流程，不代表抢购成功。消费者在提交订单后失败或失联，客户端可按 requestId 查询结果，不创建新的业务请求。

Redis 中的活动资格数与页面展示库存缓存应使用独立 key 和明确的数据模型，不能复用阶段 A 的只读库存缓存。

## 4. 库存与幂等边界

### 4.1 活动额度不能与普通购买重复出售

启动活动前，在 MySQL 中将一部分可售库存明确分配给活动，并从普通下单可售范围排除。Redis 只装载这部分活动额度。活动额度、已预占数量、已售数量、可重新发放数量必须可核对。

后续详细设计需要定义活动额度和普通 `amount/frozen` 模型之间的账务转换：活动额度分配不能再被订单重复计算为新的实物冻结；活动结束时仅释放未消耗、未预占的额度。禁止把初始活动库存直接重复灌回 Redis。

MySQL 仍保存持久订单和额度账本，并在消费事务中校验剩余额度。即使 Redis 重复发放资格，数据库也应拒绝超过活动额度的订单；用户可能收到处理失败，这一结果必须明确反馈。

### 4.2 标识和状态必须可追踪

至少区分活动 ID、可信用户 ID、客户端幂等 requestId、服务端 reservationId、订单 ID。数据库对预占 ID 或业务请求设置唯一约束；限购规则另行约束，不能只用 requestId 防止同一用户换 ID 重复抢购。

资格预占应具有“待处理、已关联订单、已释放”等状态。仅允许从合法状态转移；释放需验证状态并恰好执行一次。订单一旦持久化，后续取消或超时由订单流程负责，资格超时任务不能再自行释放同一份额度。

## 5. Redis 与任务队列的可靠性

Lua 可原子执行 Redis 内的资格检查、扣减和预占记录；它不能保证 Redis 与外部 MQ 或 MySQL 一起提交。Redis 脚本还需要避免运行时错误后的部分写入，所有可预检条件尽量在修改前检查。

实施时优先复用普通交易的 RocketMQ + MySQL 受理记录/Outbox，细化 Redis 资格预占与受理记录之间的失败恢复。以下保留候选路线比较：

| 候选路线 | 需要补齐的可靠性 |
| --- | --- |
| Redis 预占与同实例 Stream 任务写入 | 预占与任务写入设计为同一可验证操作；集群 keys 必须满足同槽要求；检查持久化、复制、故障恢复及 pending 消息重领 |
| Redis 预占后投递外部 MQ | 预占记录可扫描、可重试投递；处理发送结果未知与重复发送；消费者幂等；不能只依赖发送失败时的本地 catch |

消费成功以数据库事务提交为准，之后才确认消息。消息至少一次投递下，重复执行应查询并返回既有结果。网络超时不能直接认定建单失败，必须查询持久结果再决定重试或释放。

## 6. 故障与恢复验收

| 场景 | 期望行为 | 状态/证据 |
| --- | --- | --- |
| 同一用户重复点击或更换 requestId | 同一请求返回原结果，限购规则仍然有效 | 待实施 |
| Redis 已预占，任务未投递或响应丢失 | 可恢复投递或确认失败后释放，不永久占用名额 | 待实施 |
| 消息重复消费 | 一个预占最多创建一个订单，库存只预占一次 | 待实施 |
| MySQL 已提交，消息未确认时进程退出 | 重放识别既有订单，不重复扣减或错误释放 | 待实施 |
| 资格过期与建单并发 | 已成功建单的预占不被资格清理释放；状态与订单可核对 | 待实施 |
| MySQL 拒绝建单或活动额度不足 | 写入明确失败结果，资格按规则幂等处理 | 待实施 |
| Redis 故障、切换或记录丢失 | 暂停受影响活动或有限降级，依据持久账本恢复，禁止重装初始额度 | 待实施 |
| 队列积压、消费暂停 | 队列容量和等待时间有上限，入口停止或减少受理 | 待实施 |
| 订单取消、超时或晚到支付 | 复用已验收的订单状态规则，明确活动名额是否重新开放 | 待实施 |
| 活动结束仍有待处理请求 | 不再接收新请求，按已定义规则完成或终止在途请求后对账 | 待实施 |

## 7. 可选进阶：库存分桶

如果队列削峰后，数据库热点行仍是实测瓶颈，可将活动额度拆成多个独立桶，例如总额 10,000 分为 10 桶，每桶 1,000。请求更新不同桶的行，订单记录 bucketId，取消释放回原桶。

必须满足各桶额度总和不超过活动分配量，桶间转移不能重复发放。空桶可有限次换桶或受控调配，避免无限重试和有货买不到。不能每次更新桶后又同步修改同一条总库存热点行；汇总由账本或异步统计完成。

分桶会增加额度调配、恢复和对账成本，不列入首版默认范围。
