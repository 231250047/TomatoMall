# MQ 接入与事件方案

> 状态：订单超时单链路已实现，验证结果见 [交付记录](../实现/普通订单与超时消息.md)。PRODUCT_CHANGED 普通索引事件已实现，见 [RAG 实现](../实现/SpringAI与pgvector.md)；本文其余内容保留方案设计背景。
> 决策：统一采用 Apache RocketMQ 5.x；本轮验证组合为服务端 5.3.2、Java gRPC 客户端 5.0.7。普通订单超时使用延迟消息主触发，数据库补偿扫描兜底。
> 当前仍优先完成 [阶段 A](阶段A-交易正确性.md) 的普通交易正确性；[秒杀扩展](后续候选-秒杀场景.md) 暂缓。

## 1. 哪些业务使用 MQ

| 阶段 | 业务 | 消息方式 | 使用目的 |
| --- | --- | --- | --- |
| A | 订单超时检查 | 延迟消息 | 按订单 expires_at 触发关闭检查，减少常态数据库扫描 |
| A | 库存／购物车 Redis 缓存失效 | Outbox worker 直接调用 Redis | 当前不经过 MQ，失败重试，库存缓存 30 秒 TTL 兜底 |
| B | 商品新增、修改、下架后的检索索引更新 | 普通事件 | 将 embedding 调用、索引 upsert/delete 从商品写事务中移出，支持失败重试 |
| 后续候选 | 秒杀资格受理后的异步建单 | 普通任务消息 | 削峰、控制建单并发；当前不开发 |

这些业务并非都必须使用 MQ 才能实现；既然本轮决定引入，就复用一套代理、Outbox 和故障验证方法。普通订单创建仍同步执行 MySQL 事务，聊天流式响应继续用 HTTP 流，不因引入 MQ 改为异步建单或消息聊天。

## 2. 选型和部署边界

- 选择 RocketMQ 5.x 的延迟消息能力，避免为订单超时额外维护一套 Redis ZSet 调度。不要混用 4.x 固定延时等级示例与 5.x 客户端接口。
- 接入前验证 Java 17、Spring Boot 3.2.4、客户端依赖及本地 Docker 环境；锁定经过验证的服务端与客户端组合，记录镜像、启动方式、Topic 类型和消费者配置。
- 延迟 Topic 与普通事件 Topic 分开配置；独立业务使用独立消费组，避免缓存消费者消费掉索引任务。名称和数量以实际业务边界确定，不引入通用消息平台。
- Broker 重启、持久化卷、发送确认、消费重试及死信行为必须实测。本地单节点环境不等同于生产高可用。
- 第一版采用 MySQL Outbox 解决业务提交与发送窗口，不同时引入事务消息作为第二套发送协议。

## 3. 消息约定与可靠投递

本轮超时消息只包含 `version=1`、`eventId`、`orderId`、`expiresAt`。事件类型由专用 Topic 确定；将来的商品事件另行定义版本字段。身份、金额、地址等不放入无关消息，消费者重新读取权威业务数据。

订单/商品业务更新与 Outbox 记录在同一 MySQL 事务提交。Outbox 发送器在事务提交后读取事件，发送失败时退避重试；收到代理确认后标记已发送。发送成功但标记失败可能重复发送，保持 eventId 不变，由消费者幂等处理。

`SENT` 只代表消息已被代理接管，不代表业务处理完成。Outbox 应有待发送时间、尝试次数、最后错误及必要的领取机制；对最老未发送事件、失败积压和消费者异常告警，事件保留策略需覆盖排障与重放窗口。

## 4. 普通订单超时主流程

### 4.1 创建与定时投递

```text
下单的 MySQL 本地事务
  → 创建 PENDING 订单及商品快照
  → 条件更新 frozen 预占库存
  → 保存 expires_at
  → 写入 OrderTimeoutCheck 的 Outbox 记录
提交事务
  → 发送器立即投递延迟消息，投递时间设为订单原始 expires_at
  → 到期后消费者调用统一的订单关闭检查服务
```

消息发送重试必须使用原始 expires_at，不能每次重试再延迟 30 分钟。若发送恢复时已经过期，则立即触发检查，不能延长用户支付窗口。发布前检查部署版本支持的最大延迟范围，范围外任务不得被当成正常未来消息发送。

延迟消息只表示到期后可被消费；实际消费可能因积压或故障延后，不承诺精确到毫秒关闭。消费者以数据库保存的状态和 expires_at 再次校验，不仅相信消息内容。

### 4.2 消费与业务关闭

1. 根据订单 ID 读取权威记录。订单不存在、已支付或已关闭时不重复释放库存；不存在还需记录异常原因。
2. 若订单截止时间被变更，旧消息不能提前关闭。重设截止时间的业务必须同事务产生新超时事件；消费者早到且缺少有效新任务时补排检查，数据库扫描仍兜底。
3. 判断支付状态并按渠道规则协调查单/关单。外部请求不在长时间持有订单锁的事务中执行；结果未知时保存关闭处理中状态或持久重试任务，并保留库存。
4. 在短 MySQL 事务内重新校验并锁定订单，合法关闭者将订单转为超时关闭，按 OrderItem 快照减少 frozen，同时记录 StockChanged Outbox。amount 不因未支付取消而减少。
5. 完成业务事务后才确认消息。若交接到持久关闭重试任务，也必须在任务提交后才确认；不能只记录日志就确认处理完成。暂时性失败按客户端协议返回失败/不确认以便重试。

支付回调与超时消费者使用同一套状态约束。订单已经支付，随后收到超时消息应直接结束；无需尝试从 Broker 撤回单条已投递的延迟消息。

### 4.3 数据库扫描只作补偿

数据库保留 `expires_at` 以及关闭任务的 `next_check_at`，分别为过期待支付订单和未完成关闭任务建立合适索引。补偿任务按可配置周期分批检查超期未结束记录，调用与 MQ 相同的关闭服务，而非编写另一套解冻逻辑。

补偿扫描用于处理消息未发送、长期重试、死信、代理故障和关闭进程中断。需设置批量、速率、领取/幂等机制并监控最老未处理订单，不能全表高频扫描或无限阻塞在一条异常记录上。

原 Redis ZSet 超时投递在切换后停止；本轮迁移先人工核对旧活动订单；脚本会阻断未结清旧单，禁止将不可信的购物车数据自动转换为新预占。旧消息或旧任务重放应被状态校验安全忽略，不删除仍需恢复的数据后才切换。

## 5. 缓存失效与后续索引事件

### 5.1 库存缓存失效

当前 STOCK_INVALIDATE Outbox worker 按商品 ID 直接删除 Redis 缓存，不经过 MQ。重复删除是安全的，事务未成功时不应有该事件。Redis 故障触发重试，TTL 兜底；旧查询在删除后回填旧值的窗口仍存在，所以展示库存是最终一致，下单资格始终由 MySQL 条件更新决定。

### 5.2 商品检索索引更新

ProductChanged 由商品写事务产生，消费者读取数据库最新商品状态。新增或修改时生成 embedding 并 upsert，下架/删除时删除或使索引不可检索；文档 ID 稳定，禁止重试生成重复文档。

幂等只按 eventId 去重不足以处理乱序。需要商品版本与索引已应用版本，或对同一商品串行处理并检测过时任务；embedding 调用结束后再次验证版本，防止较早的慢任务覆盖新索引。删除需保留可判断版本的记录或 tombstone，防止旧任务把商品重新索引。无论索引同步有无延迟，导购返回前仍从业务库校验商品在售、价格和库存。
