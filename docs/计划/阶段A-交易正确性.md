# 阶段 A：交易正确性修正与验证

> 本轮实现与实测记录见 [订单改造交付记录](../实现/普通订单与超时消息.md)。本文保留最初问题分析；当前实现：单条 MQ 超时链路，缓存失效直接由 Outbox worker 执行。
> 状态：本轮代码和自动化验证已完成；真实支付宝沙箱、用户存量库迁移尚未执行。
> 目标：先使用户、订单、金额、库存和支付状态在异常及并发下保持一致，再加入 AI 写操作和高并发优化。
> 对应总路线：[PLAN.md](../../PLAN.md)。本文件维护阶段修改与验收清单；技术细节和实际结果分别维护于实现、测试目录。

**当前范围**：优先完成普通购物车结算、库存预占、支付、取消、超时及缓存最终一致性。秒杀资格预占、异步建单和库存分桶另存为 [后续候选方案](后续候选-秒杀场景.md)，不进入本阶段验收范围。

**已更新决策**：普通订单超时采用 RocketMQ 5.x 延迟消息主触发，数据库扫描负责补偿，替代 Redis ZSet 主调度。订单/库存变更和 Outbox 在同一事务内提交，缓存失效由 Outbox worker 直接执行。消息契约、迁移及验证见 [MQ 方案](MQ事件设计.md)。

## 1. 业务规则（实现与验收依据）

- 订单只能使用当前用户的购物车项；用户只能查看、发起支付或取消自己的订单。
- 商品必须在售、数量为正；成交单价由服务端取商品价格并写入 `OrderItem` 快照。订单金额由快照计算，优惠活动由服务端规则决定，前端只提供优惠券 ID 或选择，不提供最终折扣额。
- 定义 `amount` 为尚未售出的实物库存，`frozen` 为待支付订单预占库存；可售量为 `amount - frozen`，始终非负。创建订单增加 `frozen`；支付成功同时减少 `amount` 与 `frozen`；取消或超时只减少 `frozen`。每个订单只能发生其中一种终态转移。
- 同一结算请求的网络重试返回同一订单；重复支付通知、重复超时任务不得重复改变库存。
- 支付宝验签通过仍需核对商户应用、订单号、金额、交易状态。支付成功与超时同时发生时，数据库中的条件状态转移决定唯一胜者；若订单已超时却收到真实成功付款，记录异常并走查询/退款处理，不能静默丢弃。

## 2. 改造前确认的问题及场景

| 场景 | 当前代码 | 可能结果 | 修正 |
| --- | --- | --- | --- |
| 多商品结算，第二件缺货 | `OrderServiceImpl.createOrder` 103–125 行先回滚再在 `catch` 回滚 | 第一件库存多加一次 | 先写失败用例；去掉重复补偿路径，最终改为数据库事务预占 |
| Redis 扣减后，订单保存失败 | Redis 在 JPA 事务外扣减，且下单保存发生在 `try` 外 | 没有订单但库存变少 | 订单、快照和库存预占放在一个 MySQL 事务中 |
| 库存 key 丢失、服务重启预热 | `StockCacheServiceImpl.syncStock` 用 `amount-frozen` 回填，而当前下单只扣 Redis、未增加 frozen | 已下单未支付的库存重新变成可售 | 改成数据库持久预占；Redis 只缓存数据库可售量，事务提交后失效或刷新 |
| 改变或删除购物车项后付款/超时 | `reduceStock`、`releaseLockedStock` 通过购物车关系再取数量 | 扣减或释放数量错误，甚至跳过 | 全部基于不可变 `OrderItem` 快照 |
| 复制别人的购物车项或订单 ID | 下单检查 ID 是否存在；订单详情、删除和支付发起未校验所有者 | 越权下单、查看地址或操作订单 | 服务层统一按当前用户校验；接口不能自行指定用户 ID |
| 提交任意折扣额 | `CheckoutVO.discount` 为字符串，服务端按数值套用折扣 | 可能绕过优惠券资格、重复使用规则 | 服务端优惠规则/券记录决定折扣及资格，金额用 `BigDecimal.compareTo` 校验 |
| 支付回调重放、金额不符 | `updateOrderStatus` 接受 amount 却不比较；状态检查不是原子条件转移 | 错单被标记已支付或重复库存动作 | 验签后核对订单、金额、商户；仅仍持有预占的 PENDING／CLOSING→SUCCESS 成功者执行库存转移 |
| 支付与超时同时发生 | 超时任务先读 PENDING 后直接写 TIMEOUT；支付也读状态再写 SUCCESS | 两个流程都可能执行库存变更 | 以数据库条件更新或行锁串行化；只有成功转移的一方执行库存动作 |
| 定时任务处理失败 | ZSet 到期任务在处理前被弹出，`catch` 只记日志 | 订单一直 PENDING，库存长期冻结 | `expires_at` 持久化；周期扫描数据库过期 PENDING 订单兜底，任务可重放 |
| 支付表单生成失败 | `AliPayServiceImpl` 在第三方接口异常时直接删除订单并回滚 | 临时网络错误导致已创建订单消失 | 表单生成失败可重试；订单保留到过期或用户主动取消 |
| 测试回调接口公开 | `/api/orders/test-notify` 直接调用支付成功业务 | 可绕过真实支付 | 仅测试 profile 提供或移入集成测试，不在普通环境暴露 |

## 3. 推荐实现路线

### A1. 先固定业务模型与权限

1. 在服务入口取可信登录身份，校验购物车项与订单的 `userId`；支付通知是无登录态的第三方入口，仅在验签及商户信息校验后通过内部方法处理。
2. 为订单补充 `expires_at`、结算幂等键（用户范围内唯一），保留当前 `PENDING/SUCCESS/TIMEOUT` 数据的迁移映射，再决定新状态名；避免直接改枚举导致旧数据读取失败。增加用户主动取消状态时单独定义。
3. 订单商品快照由服务端价格生成，保存后用于所有库存和金额计算；订单删除区分“隐藏历史记录”与“取消待支付订单”，禁止直接硬删正在支付或已支付的订单。
4. 优惠规则从请求数值分支迁出，先保留现有满减业务但由服务端验证适用条件；若没有真实优惠券实体，不称其为优惠券系统。

### A2. 用 MySQL 事务完成库存预占与订单落库

优先选择数据库条件更新：对每个商品执行 `UPDATE stockpiles SET frozen = frozen + :q WHERE product_id = :id AND amount - frozen >= :q`，检查影响行数。多商品按商品 ID 固定顺序操作以降低死锁概率；任一失败让事务回滚，订单、订单项和所有 `frozen` 增量一并撤销。`amount/frozen` 的现有语义与数据需要先核实，必要时迁移。

支付成功事务中，在锁定订单或条件状态转移成功后，按快照执行 `amount -= q, frozen -= q`；取消/超时事务中，仅执行 `frozen -= q`。对库存字段增加数据库约束（或迁移前的数据校验）和业务断言。MySQL 提交后删除或刷新 Redis 可售库存缓存；缓存失效失败由 TTL 与对账修复。Redis 不能再独立扣减或恢复库存。

这是第一阶段的正确性方案。需要展示 Redis + Lua 高并发时，可在稳定的数据库方案上单独设计预扣和可靠补偿，并通过压测证明收益；不要在本阶段并存两套库存事实来源。

**MySQL / Redis 一致性契约**：下单、支付、取消的库存判断与修改只走 MySQL 条件更新，Redis 数值不能授权成交。因此即使缓存陈旧或 Redis 故障，也不能超卖。页面展示的 Redis 可售量允许短暂滞后；库存事务内同时写一条 StockChanged Outbox 事件，提交后由 Outbox worker 按商品 ID 直接删除缓存，读请求从 MySQL 重建。缓存设置短 TTL，兜底处理事件先于旧读请求回填缓存等竞态；Redis 不可用时从 MySQL 读取。删除缓存可重复执行，发送和消费均允许重试。缓存失效重试积压与 DB/Redis 差异进入监控。这个方案保证交易强正确、缓存最终收敛，不承诺两份库存任意时刻完全相等；若业务要求页面库存也强一致，直接读取 MySQL 或采用更严格的版本校验，不能仅靠“延迟双删”宣称强一致。

### A3. 幂等、支付及过期处理

- 结算幂等键在 `(user_id, request_id)` 上唯一；重复请求查询并返回原订单，不再次预占。支付交易号按渠道唯一，保存到账记录或支付尝试记录。
- 支付回调先验签，再核对 `app_id/seller_id`、订单、交易号和 `total_amount`；只有持有订单行锁且状态仍为 PENDING／CLOSING 且保留预占的事务可以改为已支付并消耗冻结库存。重复成功回调返回成功但不重复操作。
- 创建订单时同事务保存 expires_at 与 OrderTimeoutCheck Outbox，发送器以原始截止时间投递 RocketMQ 延迟消息；支付成功后不要求撤回消息，消费者检查终态后直接结束。发送重试不得重置支付窗口。消费者与支付回调共用订单状态约束，确认允许关闭后在一个事务内关闭并解冻；渠道结果未知时保留关闭处理中状态或持久重试任务，外部调用不持有长事务锁。数据库只对过期未完成订单及关闭重试任务做分批补偿扫描。回调若证明资金已到账但订单已过期，应留下待人工或自动退款事件，不能把库存和资金状态悄悄分叉。
- 支付页面生成失败不自动取消订单；用户可重试。取消待支付订单同样经过状态转移与库存解冻。普通删除接口只做历史记录隐藏，或先限制为不可删除。

## 5. 阶段退出标准

- [x] 订单只能由本人购物车项创建，订单详情、支付发起和取消均校验所有权。
- [x] 创建、支付、取消、超时在重复和竞争场景下各只改变库存一次。
- [x] 多商品任一缺货或数据库异常时，订单与库存整体回滚。
- [ ] Redis 重启、缓存丢失不改变已预占订单的可售量。
- [x] 金额由服务端快照和规则计算；支付通知金额与商户不符不能入账。
- [x] 支付失败可重试；过期任务失败后能重试；支付与过期冲突有可查记录。
- [x] 测试回调在正常运行环境不可访问；所有验证命令与结果已记录。
- [ ] RocketMQ 延迟消息为超时主触发，发送/消费中断和重放可恢复；DB 补偿与 MQ 调用同一业务逻辑；存量 ZSet 任务切换后无遗漏和重复解冻。

> 剩余未勾选项的边界：Redis 进程重启未实测（缓存失效／不可用已模拟验证）；真实 MQ 强杀重启已测；用户存量订单迁移、真实支付宝沙箱仍需独立验收。
