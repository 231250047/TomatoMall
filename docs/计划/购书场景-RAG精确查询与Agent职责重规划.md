# 购书场景：RAG、精确查询与 Agent 职责重规划

> 2026-09-17 规划修订；单轮查询路由与候选过滤已实施，剩余项见末尾执行记录。按 executing-plans 分任务执行；本次只调整文档。覆盖此前“先扩充各类标签，再让 Agent 解析”的建议，不改变阶段二历史代码和测试结论。

**目标：** 用户用自然语言描述想买什么，语义检索寻找相关书，字段查询查找明确对象，数据库过滤保证购买条件；Agent 决定何时使用这些能力。

**架构：** 沿用 MySQL 商品事实、Spring AI PgVectorStore 派生索引和统一商品检索服务。意图理解输出语义需求与明确约束，后端只执行白名单工具和经过校验的参数，回答基于实际商品。

**技术边界：** Java17、现有 Spring AI 1.0.0-M4、pgvector、DeepSeek；本规划不要求更换向量库、不引入多 Agent、不先建立覆盖全部图书的标签体系。框架新版本文档只作为概念参考，实际 API 在实施前核对当前依赖。写工具仍遵循原阶段 C 用户确认与幂等规则。

## 1. 重新划分三种业务能力

| 能力 | 用户在问什么 | 实现与责任 |
| --- | --- | --- |
| 语义检索 | Java入门、轻松的文学、了解印象派、类似某作品的阅读体验 | 用语义文本进行向量召回，关键词辅助，基于内容证据筛选 |
| 字段查询 | 查某ISBN、具体书名、某作者的作品；某书多少钱 | 根据商品ID、ISBN、书名或作者字段查询，必要时展示多个版本；无需强制做向量检索 |
| 精确过滤与事实核验 | 50元以下、有货、指定版本 | 后端对真实字段执行比较；召回、回退、模型回答后都不能绕过 |

“精确查询兜底”包含两个含义：向量不可用或漏掉明确书名时，用字段/关键词查询补充；数据库对价格和库存的精确校验则始终生效，不等语义检索失败才执行。

RAG 指检索后基于外部证据回答，检索来源可以是向量库、关系数据库或关键词搜索。单纯查询某书价格可以直接用数据库事实回复，不必增加生成调用。

### 主例：Java入门书，50块以下

未来工具输入示意（不是当前接口）：

```json
{
  "semanticQuery": "Java入门书",
  "filters": {
    "maxPrice": 50.00,
    "inStockOnly": true
  },
  "limit": 5
}
```

- “Java”和“入门”都保留在语义需求里，不要求商品存在 `level=入门`。
- “50元以下/不超过50元”统一解释为含50；“低于50元/不到50元”严格小于50，金额以分精确比较。
- `inStockOnly=true` 是购买推荐的默认策略，不是声称用户明确提到了库存。缺货书价格/详情查询允许返回缺货事实。
- “两本总共50元”是组合预算，不能转换成每本50元。第一版明确说明暂不支持组合预算选品，并请用户指定单本预算。
- 用户实际说“50块左右”属于弹性预算，不能擅自转换为硬上限；保留偏好，必要时澄清。

### 文学与艺术例子

- “50元内适合放松看的文学”：语义文本保留用途，价格独立过滤，不凭空生成难度标签。
- “想读余华写的小说”：已具备可靠作者字段时走作者查询并结合内容；不能将“研究余华的书”当成余华著作。
- “想看类似余华作品风格的小说”：按风格需求检索，不自动加作者=余华的限制。
- “想了解印象派，80元内”：语义检索“印象派艺术介绍”，按价格过滤，无需先定义一个覆盖全部艺术流派的枚举。
- “《活着》有货吗”：先查书名，再查实时库存；多版本显示区别，书不存在时不要用其他书冒充。

## 2. 当前实现与需要修正的地方

| 当前事实 | 后续变化 |
| --- | --- |
| 聊天大体用原问题检索，金额仅由正则处理 | Agent/查询理解将语义文本与明确价格约束分离；避免闲话稀释检索 |
| 测试集直接提供 level/excludedTopics 等字段 | 增加从原始用户输入到工具参数的端到端测试；不再用人工条件冒充理解能力 |
| level缺失时，显式难度条件会排除商品 | 导购不自动生成level硬过滤；保留“入门”语义并核对商品介绍，旧调试接口兼容 |
| excludedTopics按全文字面排除 | 导购保留“不想看源码”等原始偏好，候选选择时核验；不自动转成全文NOT包含 |
| 向量全局取200再过滤 | 修复候选截断可能漏掉预算内商品的问题，见下一节 |
| 故障降级、价格和库存复核已实现 | 保留并覆盖新路由，不能因接入Agent削弱 |

语义理解不能保证可靠识别难度或否定。商品描述不足以判断时，回答说明依据有限或澄清，不能编造标签。“不需要源码细节”与“必须完全不包含源码”也要区分。

## 3. 检索和过滤的组合方式

逻辑上的合格集合为：**与需求相关的书 ∩ 满足购买条件的商品**。工程顺序需要兼顾召回和索引时效。

### 第一版：面向当前小商品库的确定方案

1. 后端验证预算等条件，读取 MySQL 得到当前合格商品ID；此阶段没有模型决定价格是否合法。
2. 有明确商品ID/ISBN/书名等目标时走字段查询；只有预算时走商品列表，不向量化空查询。
3. 语义检索在合格ID集合内排序：给向量适配器传入合格ID过滤，使用已存的 productId 元数据；关键词路也在同一合格集合检索。Spring AI M4 的表达式语法先用真实PG验证。
4. 若M4过滤表达式不满足需求，保持对外服务契约，使用参数化PG查询实现ID范围内相似度排序；不拼接模型给出的SQL，不用全局top200后过滤充当等价实现。
5. 合并候选，由现有选品步骤核验语义与偏好；返回前再读MySQL，剔除价格变更、下架或库存不足的商品。

MySQL与PG之间不维持长事务。价格变化可能让某书暂时漏入或漏出候选，返回前核验保证不会展示已知不合格推荐；候选不足可重新检索一次，持续变化应明确反馈。推荐并不锁库存，真正预占仍在订单事务中。

合格ID方案限于当前小规模商品库；数据量增长后再按实测设计查询下推、稳定元数据过滤或搜索索引。长ID列表、MySQL全量读取和跨库一致性都必须测量，不能宣称已经解决大规模搜索性能。

### 检索不足与降级

- 向量服务异常：同条件关键词/字段查询降级，明确标记服务异常。
- 原书名精确查询为空：可尝试书名关键词或别名，显示候选；不能擅自把相似书宣称为目标书。
- 语义候选不相关：Agent最多重写一次语义查询，保留所有已确认硬约束。
- 预算内确无相关书：说明无匹配，可询问是否调整预算；未同意前不能提高上限。
- 没有资料支持“完全不涉及某内容”：说明无法核验，不能只靠向量距离保证不存在该内容。

## 4. Agent 的职责与最小工具

第一版采用受限的单个导购 Agent。模型负责理解与决策，工具服务负责查询与约束执行。

| 场景 | Agent行为 |
| --- | --- |
| 你好、谢谢 | 直接回应，不检索 |
| 明确商品ID/ISBN，或已识别完整书名 | 调用字段查询，简单规则可跳过理解模型 |
| Java入门书50元以下 | 提取semanticQuery与预算，调用语义搜索 |
| 冗长问题中夹杂个人经历 | 精炼主题，保留影响选书的需求和明确约束 |
| 上轮Java入门，这轮“再便宜点” | 结合会话需求与已返回商品理解；无法确定新上限时澄清，不凭空填写金额 |
| 搜索结果不足 | 判断重写、字段查找或澄清；不能擅自放宽硬约束 |
| “帮我买” | 第一版只读；后续按确认加购协议扩展 |

最小只读工具契约（均为规划）：

- `searchBooks(semanticQuery, filters, limit)`：主题/用途检索。filters只开放当前数据能可靠执行的价格与库存条件；原问题作为不可被改写覆盖的需求证据保留。
- `lookupBooks(productId?, isbn?, title?, author?, filters, limit)`：明确对象查询，至少一个定位字段；作者/ISBN只在元数据已规范化后开放，未支持字段明确报错。
- `getProductDetail(productId)`：商品详情、价格和库存；复用已有服务，后续对比同样读取真实事实。

后端内部可以继续复用 ProductRetrievalService/ProductCatalog，不需要为每个工具另建一套检索栈。模型返回JSON工具参数，后端白名单验证后执行；模型不能发SQL，不能提供用户权限信息。

默认每轮最多3次工具调用，语义重写最多1次；设置每次调用及整轮时间上限并记录token。阶段C接框架前验证当前依赖与DeepSeek工具调用兼容性，必要升级单独验证；不能把结构化输出解析器称为已完成自主工具调用。

## 5. 方案取舍

| 方案 | 评价 |
| --- | --- |
| 先建全面标签体系，将阅读体验和难度全部枚举化 | 数据建设大、容易漏掉无标签好书；撤回作为当前主路线的建议 |
| 只做向量检索，让模型自行判断价格库存 | 无法保证确定性约束；不采用 |
| 语义需求检索 + 字段查找 + 后端购买条件过滤，Agent编排 | 推荐；贴合描述需求、找具体书、核验购买条件三类行为 |

作者等稳定事实仍有价值，但按实际查询场景补齐；不将“大规模书目模型和分类属性改造”作为Agent的前置门槛。先规范现有规格中的必要作者/ISBN数据及测试样本，缺失时不得假装支持精确查询。

## 7. 验收数据与指标

保留既有100商品/50题及阶段二12题历史标签。新增独立40题：主题+预算10、具体书/作者/ISBN定位8、文学艺术等内容需求8、多轮6、无匹配4、服务故障/注入4。补充无level但内容适合入门、同书不同价格版本、同作者与研究作者、50元边界等商品。该题量是下一轮目标，尚未生成或运行。

分开执行：

1. 检索服务测试：人工结构化参数，定位召回与过滤正确性。
2. 端到端测试：仅给原始用户问题或对话，评估解析、路由、检索、回答；禁止偷偷将标注条件直接传入工具。

指标：主题Recall@K与排名、最终推荐相关性、明确价格约束违规率、作者/书名精确命中率、无匹配正确率、条件提取准确率、路由准确率、查询重写遗漏约束数、p50/p95延迟、模型/工具调用数与token。

确定性门槛：边界和故障回归中硬约束违规、越权、编造商品和擅自放宽约束均为0；任何违例阻止验收。语义指标与旧链路同数据对照，不设未经实测的100%准确率承诺；新增题先冻结，调优用dev，最终保留集不用于调参。工程测试执行 `mvn package`，PG用隔离 `_rag_test` 库；真实评测结果放在docs/测试，不能用计划代替已实现证明。
