# 库存一致性与下单事务

代码入口：[OrderServiceImpl](../../tomatoMall-backend/src/main/java/com/example/tomatomall/service/serviceImpl/OrderServiceImpl.java)、[StockpileRepository](../../tomatoMall-backend/src/main/java/com/example/tomatomall/repository/StockpileRepository.java)。

## Q1. 最后一件商品，两个人同时下单，怎么避免超卖？

**回答主线**：把判断和预占放在同一条数据库 UPDATE 中，检查影响行数。

```sql
UPDATE stockpiles
SET frozen = frozen + :q
WHERE product_id = :id AND :q > 0 AND amount - frozen >= :q;
```

`amount` 是尚未售出的总量，`frozen` 是未完成订单预占，二者之差是可售。若 amount=1、frozen=0，两笔各买 1 件的更新会竞争同一库存记录。前一个事务提交预占后，后一个请求条件不成立；如果前一个回滚，后一个才可能成功。

**背景知识**：普通 SELECT 后在 Java 里判断再 UPDATE，中间存在并发窗口。单条条件更新将判断与写入交给数据库执行；仅加 `@Transactional` 不会自动修复任意“先查后写”的竞态。

**追问：支付时为什么还要锁订单？** 库存条件只能保护总量下界，不知道一笔订单是否已经扣过。重复执行可能消耗别人的预占，因此还要用订单状态和订单行锁保护业务幂等。

## Q2. MySQL 为主，那 Redis 有什么用？两份数据必须一直相等吗？

**当前回答**：普通下单的成交资格由 MySQL 决定。Redis 缓存用于展示可售量，允许短暂滞后；缓存失效或不可用时读数据库。下单不再调用 Redis DECR／INCR。

例如 DB 可售为 0，而缓存仍显示 1，页面可能短暂显示有货，但下单条件更新会失败。这是展示体验问题，不会据此授权多成交一单。

**背景知识**：区分“业务事实正确”和“缓存时刻相等”。数据库事务内保存库存变更及失效任务，提交后由 Outbox worker 删除缓存，再靠 30 秒 TTL 补充收敛；不能因此宣称 MySQL 和 Redis 强一致。

**追问：不用 Redis 行不行？** 可以。低流量时直接读数据库更简单；缓存要以访问负载和延迟收益证明价值。MQ 和 Redis 都不能替代数据库库存条件。

## Q3. 数据库行锁会不会很慢？多商品会不会死锁？

**当前回答**：热门 SKU 会竞争同一库存行，这是方案的吞吐边界。事务内只做必要的数据库操作，按商品 ID 固定顺序预占，外部支付和 MQ 调用放到事务外。

**背景知识**：事务 A 先锁商品 1 再等商品 2，事务 B 反向持有时可能死锁。统一顺序能减少这类环形等待，不能保证系统永远不发生死锁。发生锁冲突或死锁时，应回滚并在需要时以同一幂等键重试整个业务事务。

**当前边界**：没有实现通用自动死锁重试器，也没有做生产热点压测。不能说条件更新“没有锁”，也不能把它称为一定无等待的乐观锁；当前没有版本号 CAS。

**追问：下一步怎么优化？** 先量测锁等待和事务耗时，再考虑限流、缩短事务、活动库存隔离、分桶或 Redis 资格预占。相关内容属于 [秒杀设计储备](../../业务项目面试准备.md)。

## Q4. 用户重复点击、请求超时重试，如何避免重复下单？

**当前回答**：前端对同一请求负载复用 requestId，后端按 `(user_id,request_id)` 唯一约束识别请求。同一用户下单先锁账户行，再查询已有订单；存在就校验摘要并返回原单，不再次预占。

**背景知识**：幂等意味着重复执行同一意图不会产生额外业务效果。禁用按钮只改善交互，无法防止网络重发、多端调用或绕过页面请求；后端必须持久识别请求。

**追问及边界**：

- **同 key 换地址？** 摘要不同，拒绝复用。
- **响应丢失，但购物项已经删了？** 先查幂等记录，再读购物项，因此能返回原订单。
- **同一商品用新 key 下单？** 属于新请求，仍要满足购物项、库存等规则；当前不是“同一商品永远只能买一次”。
- **锁账户会怎样？** 同一用户不同请求也会串行，适合当前简单模型。更细的请求占位表可后续设计，但不是现有实现。
- **只用唯一约束可以吗？** 可设计为唯一插入冲突后在新事务中查原单；不能在已经回滚标记的事务里随意捕获异常继续写。当前选择先串行再查重，路径更容易验证。

## Q5. 多商品订单第二件缺货，第一件已经预占怎么办？

**当前回答**：所有商品预占、订单、快照、购物项删除和 Outbox 在同一个本地事务内。任一条件更新失败就抛异常，整个事务回滚，不单独调用 Redis 回补。

**具体例子**：A 库存够、B 不够。A 的 frozen 在当前事务内增加，但异常后回滚；不会留下一笔“没订单的占库存”。数据库插入失败也一样。

**背景知识**：事务原子性要求这些写入使用同一个事务管理器和数据源；它不会自动包含 HTTP、Redis 或 MQ。Spring 默认代理模式下，自调用不会经过代理开启新的事务边界。本项目从独立 Handler 调用订单服务事务方法，Outbox 领取／确认用 TransactionTemplate 明确边界。[Spring 事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

**验证**：`unavailableSecondItemRollsBackWholeOrder` 和 `databaseInsertFailureRollsBackReservationCartAndOutbox`，同时断言数据库状态，不只断言接口报错。

## Q6. 为什么要订单快照？关联购物车不是更省空间吗？

**当前回答**：购物车和商品可变，交易事实不能跟着变化。订单项保存商品 ID、标题、价格、数量等快照，支付扣减和取消释放都读取快照。

**追问**：下单买 2 本后再把购物车改成 5 本，如果按当前购物车扣／退库存，就会改变原订单数量。商品改价也不应改变已确认订单金额。支付回调金额必须与保存的订单总额比对，不能信任前端金额。

**当前边界**：满减规则在服务端计算；尚未实现完整的优惠券领用、锁定、核销和退回生命周期，不能将客户端 discount 字段说成一个成熟优惠券系统。

## Q7. 提交后删缓存就一定一致了吗？

**回答主线**：还存在旧读回填竞态。

```text
读请求读到旧 DB 值 → 写事务提交新值 → worker 删除缓存
         → 慢读请求把旧值填回缓存
```

本项目靠库存缓存 30 秒 TTL 限制一次旧回填的存活时间，并以数据库条件更新保证成交正确。30 秒是缓存条目从写入起的寿命，不是任何故障下都能从数据库提交时刻起精确 30 秒恢复的 SLA。

**追问：改成延迟双删就强一致了吗？** 仍受请求耗时、第二次删除失败和时序影响，不能这样保证。对显示也要求严格最新时，可以直接读权威库；更复杂的版本化缓存需要完整处理旧版本回填。

**当前实现**：缓存失效失败由 Outbox 重试，缓存值丢失后按 `amount-frozen` 重建；这一阶段缓存事件不经过 MQ。

## Q8. 怎样排查库存不一致？管理员补货会不会破坏预占？

**当前回答**：先查 `amount>=frozen>=0`，再比对所有 PENDING／CLOSING 订单快照的数量合计与 frozen；不直接把负数或异常值归零。

管理员修改总量也走条件更新，要求新 amount 不低于 frozen。商品删除改为下架，避免有预占时把库存实体直接删掉。

[order-health.sql](../../tomatoMall-backend/db/order-health.sql) 提供核对查询。发现差异后，要结合订单、支付状态和迁移历史判断原因；当前 SQL 是人工巡检入口，不是已经上线的自动对账告警系统。

**原理补充**：锁定读适用于读取后必须排他修改的状态；本项目订单按 ID 加悲观写锁。实际锁范围取决于索引、查询条件和隔离级别，不能说任何 WHERE 条件都只锁一行。[MySQL 锁定读文档](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。
