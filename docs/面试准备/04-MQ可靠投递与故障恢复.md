# MQ 可靠投递与故障恢复

当前仅接入订单超时消息。缓存失效由 Outbox worker 直接调用 Redis；商品索引 MQ、秒杀异步建单尚未实现。

代码：[OutboxWorker](../../tomatoMall-backend/src/main/java/com/example/tomatomall/order/OutboxWorker.java)、[RocketMqTimeoutTransport](../../tomatoMall-backend/src/main/java/com/example/tomatomall/order/RocketMqTimeoutTransport.java)。

## Q1. 数据库提交成功，但发消息失败，怎么办？

**回答主线**：订单、库存预占和 Outbox 事件在同一个数据库事务提交，后台负责投递。发消息不放在下单事务中，也不只靠内存 afterCommit 回调。

**背景知识**：数据库事务与 Broker 发送是两个系统的操作。先发消息可能导致数据库回滚但消息已经存在；先提交数据库再普通发送，可能在两步之间崩溃。Outbox 把“需要发送”这件事持久化，使业务提交后仍能找到待发送工作。[事务 Outbox 模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

**追问：Outbox 就是分布式事务吗？** 它没有让数据库与 Broker 形成一个原子的共同提交。它用本地原子写入、可重试投递和消费幂等来完成最终处理。数据库自身的持久性与备份仍然是前提。

## Q2. 你如何保证消息不丢？

先给出边界：当前方案保留可恢复工作记录，处理已验证的失败窗口，不能概括成任何故障下“绝不丢失”。按三个阶段回答：

| 阶段 | 当前保护 | 仍需关注 |
| --- | --- | --- |
| 业务提交到发送 | 同事务 Outbox；未确认就不标 sent，失败重试 | 数据库故障、积压、清理策略 |
| Broker 接收与持久化 | 当前测试实例同步刷盘；做过确认后强杀原存储重启 | 单节点磁盘损坏不等于已解决，多副本部署未验收 |
| 消费到业务完成 | 提交业务事务后再返回 SUCCESS；异常返回 FAILURE | 重复、死信、永久业务异常和人工处置 |

**生产者发送超时**是最常见追问：可能没发出去，也可能 Broker 收到但确认丢了，所以重试同一 eventId，并接受可能重复。Outbox 的 sent 只说明发布阶段收到确认，不代表订单已经关闭。

## Q3. 重复消费怎么处理？只用 eventId 去重够吗？

**当前回答**：超时检查以订单行锁和状态机实现业务幂等。第一次关闭把状态和库存一起提交，第二次看到终态直接返回。支付回调也是同一原则。

**背景知识**：若先写“已消费”标记后处理业务，中途失败会漏处理；若先执行业务后独立写标记，中途失败会重复执行。若使用去重表，它应与业务变更放在同一个事务中。

**当前边界**：没有实现通用消费去重表，eventId 是事件身份和排查依据，不是“收到同 ID 就永远跳过”的独立逻辑。不同事件也可能检查同一订单，所以订单状态才是最终业务保护。

**追问：将来发送邮件也靠状态机吗？** 外部副作用不在本地数据库事务内，需要另行设计幂等请求号、发送记录或渠道去重能力，不能直接复用一句“我们有行锁”就解决。

## Q4. 什么时候 ACK？处理失败一定要无限重试吗？

**当前实现**：

- 本地终态事务成功或发现已经终态，返回 SUCCESS。
- 查单结果 UNKNOWN，但 CLOSING 与 next_check_at 已提交：可以 ACK，本次工作已持久交给数据库补偿。
- 消费解析失败或业务处理抛异常：返回 FAILURE，进入 Broker 消费重试策略。

**背景知识**：ACK 是向 Broker 表示本次消费责任已被可靠处理／交接，不一定表示订单已关。关键是不能只把异常写到日志，丢掉所有持久恢复入口后就 ACK。

**追问：毒消息怎么办？** 暂时网络错误适合退避重试；格式永久错误、缺失快照、库存数据损坏需要修复或人工核对。当前没有错误类型分流与完整死信运维界面；不能把所有异常无限快速重试，也不能为了清队列盲目 ACK。

## Q5. 两个实例会不会同时发同一条 Outbox？租约能彻底防重吗？

**当前回答**：查询候选后，在短事务中锁事件行并二次检查，领取 60 秒租约。完成发送后再锁行，只有 leaseToken 匹配才能确认。发送在数据库事务外进行。

**故障时序**：

```text
worker A 领取 token-A → 卡住超过 60 秒
worker B 重新领取 token-B → 发送成功
worker A 恢复 → 也可能发送成功 → 但不能用 token-A 确认 token-B 的任务
```

**背景知识**：租约有有效期，进程暂停、慢网络和时钟差都可能让旧持有者在失效后继续执行。当前 token 的保护范围是 Outbox 确认记录，不会阻止 Broker 接收旧 worker 的发送；消费幂等仍然必需。

当前有过期租约恢复及旧 worker 不能确认新租约的测试。没有实现租约续期或 SKIP LOCKED 批量领取，后者属于吞吐优化候选。

## Q6. MQ 宕机了，还能下单吗？

**当前回答**：在 MySQL 等必要服务正常时，当前下单事务不需要 Broker 同步可用，可以提交订单和 Outbox；发布者保持失败重试，数据库扫描仍可处理到期订单。

**不能省略的边界**：长期故障会积压事件，占用存储和补偿处理能力。生产中应按积压量、最老未发送时长、业务延迟设告警与限流／降级阈值，不能无限接受请求。

**当前代码**：MQ 连接有定时重试；发送失败退避。实际最大间隔 256 秒，公式和字段见 [代码边界说明](../实现/订单代码链路与事务边界.md)。补偿扫描每轮 100 单，需评估故障期间的新到期订单速率是否大于处理速率。

已有巡检 SQL 和日志，完整告警与自动降级策略还未实现。

## Q7. MQ 已经有重试了，为什么还有 Outbox 重试和数据库重试？

它们解决不同阶段的问题：

| 重试层 | 工作事实在哪 | 负责的窗口 |
| --- | --- | --- |
| Outbox 发布重试 | outbox_event | 业务已提交，但消息尚未确认发布 |
| Broker 消费重试 | Broker 的消费记录 | 消息已发布，但消费失败／ACK 不明确 |
| 订单补偿重试 | orders.next_check_at | 渠道结果未知，或超期订单未完成关闭 |

同一笔业务可能被多个入口重复触发，因此都要调用同一个幂等关闭服务。当前补偿扫描并不独占领取订单，重复入口还可能造成重复查单；后续可优化请求合并与限流，但终态事务必须继续保留幂等保护。

## Q8. 延迟消息重发、晚到、早到和乱序，分别怎么处理？

- **发送重试**：使用原 expires_at，不能重算 `当前时间+30分钟`。
- **晚到**：如果已支付就退出；仍未完成就进行关闭核对。
- **早到**：根据数据库 deadline 再次判断，不提前释放；数据库扫描仍保留后续恢复路径。
- **支付完成后的超时消息**：状态检查后退出，不必从 Broker 撤回消息。
- **同一订单多次检查**：订单状态保护结果，不依赖消费顺序。

**背景知识**：本项目没有使用有序 Topic，也没有要求支付通知与 MQ 全局有序。消息的时间戳用于投递，消费者最终依据数据库事实处理。官方说明过去的投递时间会导致立即投递；本项目重发过期原始 deadline 已有实际 Broker 测试。[RocketMQ 延时规则](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)。

**追问：如果支持延长支付时间？** 当前没有修改截止时间的业务接口。后续必须同事务修改 deadline 并产生新检查事件，旧消息读取新 deadline 后不得提前关单；不要把这个未来设计说成现成能力。

## Q9. 消息积压了，怎么排查和恢复？

**先区分积压位置**：Outbox 没发出、Broker 没消费、还是消费者一直因渠道未知而交接数据库重试。三者指标不同，不能只看队列长度。

**建议排查顺序（运维设计，未全部实现）**：

1. 看最老任务年龄、增长速率、失败次数与错误分类。
2. 确认数据库慢 SQL／锁等待、支付渠道耗时、Broker 可用性及消费者状态。
3. 临时错误恢复后，限速补偿，避免回放瞬间压垮数据库和支付接口。
4. 永久坏数据先修复；死信重放保持业务标识并检查当前终态，不能直接把订单强制改为已关闭。
5. 根据实测扩消费者或优化领取，但热点库存／订单行本身可能限制收益。

可直接展示的入口：[order-health.sql](../../tomatoMall-backend/db/order-health.sql)。Outbox 保留与清理尚未自动化；不能提前删掉仍需追踪或恢复的记录。

## Q10. 为什么选 Outbox，而不是 RocketMQ 事务消息？后续哪些业务适合 MQ？

**当前取舍**：订单、快照和库存本来就在同一 MySQL 事务里，附带一条事件记录容易形成可查询、可重试的发布任务；暂时只维护一套发布一致性方案。代价是额外表、轮询、租约和清理工作。

事务消息是可讨论的替代方案，需要单独设计本地事务状态与回查协议、验证所用版本和消息类型的适配；不能认为名称带“事务”就自动让数据库、Redis、支付平台原子提交。本项目没有实现事务消息，也没有做两种方案的性能对比。

**按项目阶段区分**：

| 业务 | 当前状态 | 需要补充的设计 |
| --- | --- | --- |
| 订单超时检查 | 已实现，真实 Broker 验证 | 生产运维、容量和沙箱继续验收 |
| Redis 缓存失效 | 已用 Outbox 直接执行 | 现阶段无需增加 MQ 消费者 |
| 商品变更后更新检索／向量索引 | 后续计划 | 商品版本、乱序防护、下架删除、embedding 失败重试 |
| 秒杀资格受理后建单 | 后续候选 | 预占与可靠受理、重复建单、释放及故障恢复 |
| Agent 触发交易动作 | 后续设计 | 用户确认、身份传播、业务幂等、审计；并非所有工具调用都应异步 |

索引更新中仅按 eventId 去重，无法阻止旧版本覆盖新版本；这是与超时状态检查不同的幂等问题。后续扩展时应按业务重新设计，而不是直接套一层通用消费者。
