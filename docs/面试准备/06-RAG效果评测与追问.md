# RAG 效果评测与追问

> 更新口径：已完成 [真实模型首次试验](../测试/2026-09-17-真实模型首次评测.md)：三策略各 50 题、生成 10 题。纯向量标注召回有改善但负例更多，混合检索尚无整体优势；生成 5 题呈现模型选品引用、4 题回退、1 题检索为空。以下未接入的表述属于此前基线，不能作为当前状态；首次试验也不代表完成独立质量验收。

口径日期：2026-09-17。这里区分已经完成的工程与关键词实验、尚待真实模型验证的效果，避免面试时夸大。

## 1. 你的商城 RAG 是怎么实现的？

**建议回答：** 我将商品介绍和规格转成文档，用 Embedding 向量化并通过 Spring AI PgVectorStore 存入 PostgreSQL。查询使用关键词和向量召回，以 RRF 融合排名，再读取 MySQL 的最新状态过滤价格、库存和上下架。候选提供给 LLM 选品，后端验证商品 ID 和引用，最终价格等事实由数据库提供。商品变更通过同事务 Outbox、MQ 消费和定时核对同步派生索引，跨库是最终一致。

**追问边界：** 当前关键词是小目录规则检索，不是 BM25；未接入 reranker。当前文档是短商品文本，不要说已经做了复杂 PDF 分块。实现细节见 [RAG 与商品索引一致性](05-RAG与商品索引一致性.md)。

## 2. 你知道 RAG 是怎么测试的吗？

**建议回答：** 我会分检索、生成和业务三层。检索用 Hit、Recall、Precision 和排序指标；生成看忠实性、相关性、正确性与完整性；业务看预算、库存、商品事实、无匹配、延迟与成本。用固定标签和程序校验客观事实，人工或 LLM judge 评审语义。分开组件实验与端到端实验，才能定位问题出在召回、约束理解还是生成。

**追问：忠实性与正确性有什么区别？** 忠实性看回答是否依据给定资料，正确性看是否符合真实事实。资料过期时，忠实复述也可能答错；商城价格和库存应查当前数据库。

## 3. 你是如何测试项目的 RAG 效果的？

**建议回答：** 我建立了 100 件合成商品、50 条问题的固定评测集，记录相关商品、禁止商品与预算库存约束，使用真实 MySQL 和共享检索服务生成关键词预测，再用 Python 确定性评分。开发集 30 题、保留集 20 题，有匹配题的 Hit@5 是 29/29 和 18/19；但混入禁止商品的题目分别有 11 和 2 条，所以同时报告查询通过率。固定向量的 PG 集成测试另外验证持久化与故障处理。真实 Embedding 与生成 LLM 的质量对照还没完成，不能把这些结果称为完整 RAG 准确率。

**追问：有没有接入 Ragas？** 当前没有。现有客观标签和业务规则直接用 Python 评分；将来可引入 Ragas 等工具辅助生成评审，但工具不能替代数据、标签与实验设计。

## 4. 命中率高，为什么整体效果还不一定好？

找到一件合适商品，同时推荐四件不合适商品，Hit 仍为 1。当前要求“找全标签、没有禁止结果、满足硬约束；无匹配题返回空”的查询验收通过数是 19/30 和 17/20，合计 36/50。这比只报命中率更能暴露错误候选问题，但仍不等于真实用户满意度。

## 5. Precision、Recall、Hit、MRR、NDCG 有什么区别？

- Hit：至少找到一个目标的题目比例。
- Precision：前 K 条里有多少相关，关注噪声。
- Recall：标注相关商品找到了多少，关注遗漏。
- MRR：首个相关结果排得多靠前。
- NDCG：结合分级相关性和排名，关注好结果是否优先展示。

例如相关集合 A、B，前五条只有第 2 条是 A：本题 Hit=1、P@5=1/5、R@5=1/2、倒数排名=1/2。项目 P@5 使用固定分母 5，且标签不穷尽，不能把约 20% 直接解释为业务准确率。MRR、NDCG 是我了解的通用指标，当前实验没有报告这两项成绩。

## 6. 测试集全面吗？标签是谁定的？

尚不全面。商品、问题和规则标签由开发过程构造，没有独立人工复核，技术书占比较高，只有两条无匹配题。当前适合做可重复回归，不足以代表真实用户分布。后续补真实或脱敏用户表达、错别字、难度偏好、更多负例与无匹配样本，再由独立评审者复核。

**追问：保留集有没有泄漏？** 当前保留集已经跑过并用于问题分析。若基于这些结果调参，就不能继续称它为完全未见数据，需要新建验收集。

## 7. 你怎么证明向量检索或混合检索比关键词好？

目前尚未证明。后续冻结同一份商品、查询、标签和 topK，分别跑 keyword、真实 vector、hybrid，对比逐题相关性、错误候选、违规和延迟；保留超时和降级结果。不能一边更换题集一边更换方法，也不能把故障退回关键词后的命中算作向量效果。必要时分别改变融合、阈值等因素，定位收益来源。

## 8. 你的测试能证明 LLM 理解预算并正确推荐吗？

当前检索采集器把结构化 constraints 一起提交，所以主要证明检索和过滤。要测完整链路，需要只提交自然语言，记录约束处理、召回候选、模型选择及最终结果，检查所有要求是否满足。还需真实模型响应，不能用降级的事实列表代替生成质量成绩。

## 9. 如何判断模型有没有幻觉？引用原文就够了吗？

先核验 ID、金额、状态和库存等客观事实，再检查生成断言有没有证据支持。引用原文存在只证明文本来自候选，不证明它与用户需求相关，也不证明难度和用途合适。当前代码有候选 ID 和原文引用校验，真实推荐质量仍需人工或经校准的 judge 评审。

## 10. 用另一个 LLM 评分可靠吗？

它可以批量辅助评审，但会受提示词、模型偏好和随机性影响。应固定评分标准与模型版本，用人工样本检查一致性，保留分歧并复核。库存、预算和商品存在性用程序判断。不能生成模型自己打高分就认为业务效果好；不同 judge 也不天然是正确答案。

## 11. 索引和 MQ 测试通过，不就说明 RAG 好了吗？

工程测试验证的是数据持久化、幂等、回滚、重试和权限等约束。固定向量可以精确控制预期，适合验证存储链路，却没有真实语义分布。真实 broker 重投实验中索引可能使用故障 double，也不能宣称已经做了整个跨库链路的所有故障演练。工程、检索质量、生成质量、性能四类证据分别报告。

## 12. 项目现在需要哪些 API？

按当前适配：DashScope Embedding 用于商品与查询向量化，DeepSeek 用于候选选品和引用生成。只有生成模型也可以测试关键词召回后的 LLM 链路，但不能验证向量质量；只有 Embedding 则能评测语义检索，不能验证生成。judge 是可选的，初期可以人工评审。换供应商需核对代码适配，不是任意 key 都能直接用。

## 阶段二追问：为什么检索命中仍可能推荐失败？

检索召回、候选过滤、模型选择是三个边界。q32 已召回 79.99 元的书，但上下文没提供价格，模型无法核验预算而拒绝；现在传入实时价格事实。q35 暴露单一阈值和融合截断可能漏掉合适书，因此选品保留两路候选，再由模型筛选。不能用 Recall@5 代替最终回答正确率。

**为什么不一律提高相似度阈值？** dev 集无匹配题最高相似度约 0.532，而部分正确结果只有 0.523。提高到 0.54 会减少误召回，也损失相关结果；需要报告取舍。RRF 分数只是名次融合，不是相关概率。

**模型读懂“不要源码”了吗？** 本次仅支持结构化 excludedTopics 字面过滤。自然语言提取、历史补全和意图路由放在 Agent 层；服务端负责验证参数和执行过滤，不盲信模型。

**怎么证明有效？** 先用 dev 调阈值，再跑旧 heldout 与冻结新题；保存原始响应、预测、失败案例，并单独测生成。开发者编写的合成题有偏差，不能声称真实用户准确率。具体分数、成功与失败例子见[阶段二报告](../测试/2026-09-17-RAG阶段二修复验证.md)。

## 购书Agent追问：语义相关与精确条件如何分工？

“Java入门书50元以下”中，Java入门是语义需求，价格是数据库硬条件；后端固定融合策略，Agent不能给权重或放宽价格。明确书名/作者/ISBN走字段查询，类似作者风格走语义检索。用原话端到端测试工具选择，另用确定性测试验证价格49.99/50/50.01边界。

**先取topK再过滤有什么问题？** 全局候选可能被贵书占满，合格书漏召回。本项目用MySQL合格ID约束PG查询，真实测试构造205本更相似的贵书后验证预算内目标仍出现；该方案面向小商品库，并未证明大规模性能。

**这算完整Agent吗？** 已有原生模型工具选择和受控执行，是单轮只读编排；没有实现任意循环、多轮记忆、写操作。详见[实现](../实现/购书Agent与检索策略.md)和[评测](../测试/2026-09-17-购书Agent验证.md)。
