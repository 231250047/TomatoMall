# 超时订单与支付竞争

对应：[关闭处理器](../../tomatoMall-backend/src/main/java/com/example/tomatomall/order/OrderTimeoutHandler.java)、[支付网关实现](../../tomatoMall-backend/src/main/java/com/example/tomatomall/service/serviceImpl/AliPayServiceImpl.java)、[状态与事务边界](../实现/订单代码链路与事务边界.md)。

## Q1. 你是怎么实现“30 分钟未支付自动关闭”的？

### 60 秒回答

> 下单时把 expires_at 保存到 MySQL，并在同一个事务写超时 Outbox。后台投递 RocketMQ 延迟消息，投递时间始终使用这个原始截止时间。消息到达后先查数据库，订单已支付或已关闭就结束，还没到期也不关闭。需要关闭时先短事务转 CLOSING，然后在事务外查询和关闭支付渠道交易；确认可关闭后，再用一个事务改变终态并释放该订单的预占。消息故障和支付结果未知由数据库补偿扫描继续处理。

### 展开逻辑

1. 截止时间属于业务数据，重启后仍可查询。
2. 延迟消息表达“现在应该检查”，不直接授权“立即释放库存”。
3. 已付、未付、渠道结果未知必须分开处理。
4. 关闭状态和解冻同事务提交，不能分成两个成功与否独立的操作。
5. 支付完成后无需撤回已投递的消息；晚来的检查读取 SUCCESS 后退出。

**背景知识**：使用 RocketMQ 5.x 的绝对投递时间，需要 DELAY Topic；到期表示消息可进入消费过程，并不保证应用业务在该毫秒完成。积压、重启、重试都会增加实际关闭延迟。[官方延时消息说明](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)。

## Q2. 为什么既用 MQ，又保留数据库扫描？直接定时任务不行吗？

**回答主线**：低流量项目可以先只用数据库扫描。本项目接入 MQ 后，由延迟消息做常态触发，扫描负责恢复超期订单和持久关闭任务，两者调用同一套业务逻辑。

**方案取舍**：

| 方案 | 优点 | 需要解决的事情 |
| --- | --- | --- |
| 数据库定时扫描 | 依赖少，任务事实与订单一起持久化 | 索引、批量和扫描延迟；积压时处理能力 |
| JVM 定时器／内存延迟队列 | 简单，适合进程内调度 | 重启丢任务，多实例协调，需额外持久恢复 |
| Redis ZSet | 可排序取到期任务 | 出队到业务完成之间的崩溃窗口，需要领取／确认／重试协议 |
| MQ 延迟消息 | 时间触发与业务处理分开，可使用消息重试机制 | 本地事务与发消息一致性、重复消费、运维和补偿 |

**本项目原问题**：旧 ZSet 路径取出就删除任务，再分步改订单和库存；任何一步失败都可能失去恢复入口。问题在于可靠处理协议缺失，不能简单归因于 Redis 不可靠。

**当前边界**：默认扫描每 60 秒最多 100 个候选订单，这是实现参数，不是保证 60 秒内清空任何积压。单实例按批量和扫描间隔粗算，理想上限约 100 单／分钟，实际还受处理耗时影响；大量积压时要专门评估补偿容量。

## Q3. 支付回调与超时同时到达，谁赢？

**回答主线**：先核实渠道结果，再通过订单行锁和状态约束决定本地库存转移；不能仅按消息到达先后来判断钱有没有付。

| 交错情况 | 当前处理 |
| --- | --- |
| 支付事务先提交 SUCCESS | 超时读到终态，不释放库存 |
| 超时先转 CLOSING，随后收到有效支付通知 | 允许 CLOSING 转 SUCCESS；关闭事务再次检查时不释放 |
| 渠道关单失败，可能正在支付 | 本地不猜测成功，保持 CLOSING 并重查 |
| 本地已 TIMEOUT／CANCELLED，又收到有效付款证明 | 保持关闭终态，记录 PAID_AFTER_CLOSE，进入核对／退款处置 |

**背景知识**：订单行锁只协调本地数据库事务，不能锁住支付平台。必须结合外部查询／关单结果处理跨系统竞争。

**追问：超过 30 分钟的付款通知是不是都拒绝？** 不是。通知可能延迟，且资金可能已到账；当前对仍持有预占的 PENDING／CLOSING 允许核对后记为 SUCCESS。已释放库存则走异常处置。deadline 控制新的本地支付发起和关单检查，不等于可以丢弃迟到的资金证明。

## Q4. 为什么需要 CLOSING？不能直接 PENDING→TIMEOUT 吗？

**当前回答**：查单和关单可能慢、超时或结果不确定，需要一个持久状态表示“已经开始关闭，但还不能释放预占”。它同时阻止新的正常支付发起，并给扫描器留下重试入口。

**背景知识**：外部调用超时只表示没有及时得到响应，不代表操作一定失败，也不代表没有支付。若此时直接解冻并卖给下一个人，稍后收到已付通知就可能出现资金已收、库存已分配的问题。

**为什么不在一个长事务里查单？** 长时间持有订单锁会阻塞回调等请求，增加锁等待和连接占用，而且数据库回滚并不能撤销远端已经发生的支付动作。

**当前实现**：`prepareTimeout` 提交后，Handler 才调用网关；随后 `finishTimeout` 或 `updateOrderStatus` 再开启短事务、重新读取并校验。方法名带 Timeout，但主动取消也复用这条关闭流程。

## Q5. 用户从来没付款，为什么还可能一直关单中？

必须区分两种情况：

- **从未发起支付**：`payment_attempted=false`，关闭处理可直接按本地状态释放。
- **生成过支付表单**：用户可能未打开页面，也可能已跳到渠道。查询失败或查无交易不能在当前实现中直接认定“安全释放”。

**当前真实边界**：TRADE_NOT_EXIST 也保守归为 UNKNOWN；下一次扫描重试，第 10 次起记录 payment_incident，但不会因此强制解冻，也不会停止重试。异常名称中的 EXHAUSTED 不代表代码已经停止重试。

**面试回答**：我优先保证资金和库存安全，因此这类订单可能长时间占库存，是明确的待完善点。后续需要验证渠道绝对截止时间、迟到表单和查单语义，完善支付尝试记录及对账／人工处理闭环，再决定哪些情况可自动安全释放。不能仅加一个本地超时就认定远端绝无付款可能。

这部分尚未经过真实支付宝沙箱端到端验收，应明确说明。

## Q6. 用户主动取消和超时取消有什么区别？

**共同点**：都要校验合法状态，都不能在资金结果未知时直接释放，最终库存变化只发生一次。

**当前差异**：主动取消要验证归属，记录 cancel_requested 并进入 CLOSING；可以在未到 deadline 时启动关闭流程，确认关闭后是 CANCELLED。自然到期关闭则是 TIMEOUT。SUCCESS 不能走取消接口，应走退款业务。

**追问：直接删除订单不就取消了吗？** 删除记录不能代替终态转移、库存释放和渠道关单。当前 DELETE 只隐藏终态订单，交易快照和异常核对依据仍保留；结算时移除的购物项在取消后不会自动加回。

## Q7. 浏览器跳转显示“支付成功”，能直接改订单吗？

**当前回答**：不能。浏览器参数不构成可信付款证明。returnUrl 只做导航；notify 验签后还要核对 app_id、seller_id、订单金额和交易号，事务内验证状态。

**背景知识**：验签证明通知来自相应签名主体且内容未被篡改；业务校验确认这笔通知确实属于本商户、本应用和这笔订单。只验签而不核对业务字段仍不完整。

**当前实现**：免验签的 test-notify 已删除。测试用可控网关和本地生成的 RSA 密钥验证流程，未使用真实付款。所有权校验还覆盖详情、购买历史、支付发起和取消。

## Q8. 进程在关单中间挂了，怎么恢复？

| 崩溃位置 | 恢复依据 |
| --- | --- |
| CLOSING 提交前 | 本地事务回滚；仍由未完成订单和消息触发检查 |
| CLOSING 提交后，调用渠道前 | next_check_at 已持久化，数据库扫描重新查单 |
| 渠道实际已关闭，本地还没确认 | 再次查询确认渠道状态，然后尝试本地终态事务 |
| 本地已释放，ACK 前 | 消息可能重投；终态判断阻止第二次释放 |

**追问：必须靠原进程内存才能重试吗？** 不需要，订单状态、下一次检查时间与快照都持久化。但恢复仍依赖数据库可用、补偿任务运行和渠道最终可确认；不能承诺任意永久故障下自动完成。

验证入口：`unknownPaymentRetainsStockAndDatabaseScanCanRetry`、`paymentAndTimeoutRaceHasOneInventoryEffect`、真实 `RocketMqTimeoutIT`。
