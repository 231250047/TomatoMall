## 1. 本次变更和证据范围

用户配置两类 API Key，并指定请求模型 `deepseek-v4-flash`。DeepSeekServiceImpl 从配置读取模型和 Base URL，替代硬编码，普通对话和带 prompt 调用共用配置；URL 接受带或不带 `/v1` 的基础地址。模板默认模型改为用户指定名称。本机私有配置同步更新，密钥不写入本报告。

官方说明旧名称仍可调用，但实际服务已切换到 V4.1 Flash；本次最小调用请求 `deepseek-v4-flash`，响应 model 为 `deepseek-flash`，正文非空。不能宣称锁定了旧版 V4 权重。[DeepSeek 官方说明](https://api-docs.deepseek.com/zh-cn/)

Embedding：DashScope `text-embedding-v4`，实际返回 1024 维。独立 MySQL `tomatomall_fixture_rag_eval`、独立 PG `tomatomall_real_rag_eval`、Redis DB14，18080 应用关闭订单与商品 MQ 消费，索引构建为 SUCCESS；100 件商品处理完成，其中 99 件在售商品有向量，下架条目不入索引。

本次采用现有数据与标签，没有调阈值或修改标签。50 题分别采集 keyword/vector/hybrid，共 150 次检索；另选 10 题调用真实 recommend 链路。后者是开发试验，不是全面或独立验收。

| 策略 | 集合 | 标注 P@5 | 标注 R@5 | 禁止商品问题数 | 无匹配正确 | 硬约束违规 | 降级 |

| hybrid | heldout 20 | 0.1895 | 0.9474 | 5 | 1/1 | 0 | 0 |

结论：纯向量在已知保留集上的标注召回比关键词更高，但禁止结果更多；混合方案没有体现出整体优势。当前 0.3 阈值与 RRF 参数尚未通过独立题集调优，不可宣称“接入向量就显著提升推荐效果”。硬约束仍由结构化过滤保证；这批 search 请求直接携带题集中 constraints，不能当成自然语言约束理解成绩。

所有模式使用同一数据、topK=5；既有标签不穷尽，P@5 解释和数据局限继续适用。结果见 [metrics](结果/rag/2026-09-17-real/metrics.json)，逐题预测和原始响应在同目录。

## 9. 当前 chunk 与用户 query 的处理方式

### 文档侧：一件商品作为一个检索单元

`ProductDocuments.text()` 把书名、分类、简介、详情、排序后的规格合并；`document()` 创建一个 Document，稳定 ID 由 productId 生成，metadata 保存 productId、contentHash、textVersion。没有调用 TextSplitter，没有逐章分块或 overlap。当前资料是简短商品介绍，保持同一本书的信息完整；价格与库存不写入向量正文，而是回查 MySQL。

下面是 q01 第一条结果实际保存的 evidence，也就是对应商品的索引正文：

```text
书名：Java第一步（合成测试）
分类：science
简介：合成测试图书，主题：Java；难度：入门。内容：变量、循环与面向对象基础。
详情：本商品为商城检索评测编写的虚构资料，不对应真实出版物。适合入门学习者。学习目标：变量、循环与面向对象基础。前置知识：无。
规格：主题：Java；前置知识：无；学习目标：变量、循环与面向对象基础；适用难度：入门
```

### 查询侧：完整短问题直接向量化

对用户示例“我想学习java，请你给出相关的书籍推荐”，当前链路是：

```text
完整用户问题
→ ProductSearchQuery：trim、校验长度、尝试提取金额范围
→ ProductRetrievalService：把完整 query 交给向量索引
→ PgVectorStore：对完整 query 做 Embedding 并搜索
→ 混合模式同时运行关键词规则，再以 RRF 融合
→ MySQL 过滤在售／库存／价格，取前 5 件
→ LLM 根据完整用户问题与候选选品、摘录原文
→ 后端核验并组装最终回复
```

这句用户示例没有列入本次 50 题，也没有新发 API 请求；以上是根据代码说明处理路径，不是该句的实测结果。当前不会把它改成“java学习”，也不会把问题切成多个 chunk。金额提取不会从原始 query 中删掉金额文字；对多轮指代也没有查询重写模块。关键词支路会去除部分常见词、提取英文词和中文双字片段，这与向量支路的完整问题输入不同。

### Chunking、分词、查询改写的区别

| 概念 | 处理对象 | 示例 | 当前实现 |
| --- | --- | --- | --- |
| 文档分块 Chunking | 待入库的长资料 | 将章节切为多个语义完整段落 | 一件商品一个 Document，未进一步拆分 |
| 分词／tokenization | 文本内部表示或关键词搜索 | 模型 tokenizer；关键词支路英文词、中文双字片段 | SDK／模型内部 tokenization；另有关键词规则 |
| 查询改写 Query rewriting | 用户问题 | 把带指代的追问补全成可独立检索的问题 | 尚未实现 |
| 约束提取 | 用户需求 | “每本不超过80元”→ maxPrice=80 | 当前部分金额用正则提取；并非完整意图理解 |

Spring AI 的 TextSplitter 属于入库 ETL 的 DocumentTransformer，用于把文档分成适合模型窗口和检索的片段；它不等于把用户问题简写成关键词。[官方 ETL 说明](https://docs.spring.io/spring-ai/reference/1.0/api/etl-pipeline.html)。这只是概念参考，不表示项目已引入该 splitter。

“java学习”可以作为后续查询改写的一个候选，但不是必需或必然更好。完整问题可能包含零基础、源码、用途和排除偏好；缩成两个词可能丢失意图。后续若引入改写，应保留主题、难度、用途和硬约束，分别对比原问题、改写问题和融合检索效果，不能凭直觉替换所有输入。

若未来加入长篇试读或知识文档，再按章节／段落及 token 上限分块，保留 productId、章节、chunkId 和源版本；召回后按商品聚合去重，并完善整本更新／删除对应所有 chunk 的机制。当前未实现这些长文档能力。
