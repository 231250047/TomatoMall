## 1. 当前到底测到了哪一层？

| 层次 | 当前证据 | 尚未完成 |

| 关键词检索质量 | 真实 MySQL、统一检索服务、100 商品和 50 题预测评分 | 独立新题与更充分标签 |

## 2. 通用评测指标

### 2.1 检索：有没有找对、找全、排好？

设某题标注相关集合为 R，前 K 个返回结果为 T。

| 指标 | 定义与用途 | 注意事项 |
| --- | --- | --- |
| Hit@K | 前 K 条至少命中一个相关结果的题目比例 | 命中一个不代表其他候选合适 |
| Precision@K | `相关命中数 / K` | 本项目不足 K 条仍除以 K；标签不全会低估相关性 |
| Recall@K | `相关命中数 / 该题相关标签总数` | 无相关标签题单列，不除以零 |
| MRR | 各题首个相关结果排名倒数的平均；未命中记 0 | 若截断在 K，需标明 MRR@K |
| NDCG@K | 按相关等级与位置折损累加得 DCG，再除以理想排序 IDCG | 可用 0/1/2 分级标签；需统一增益规则及无相关题处理 |

例如 R={A,B}，返回 [C,A,D,E,F]：本题 Hit=1、P@5=20%、R@5=50%、倒数排名=1/2。多标签问题中，Hit 和 Recall 不相同。

本项目商品是检索单元；文档型 RAG 通常以文档或 chunk 为单元。Ragas 的 Context Precision/Recall 有不同实现，其中一些依据模型判断或参考答案事实点评分，不能把其数值与这里的商品 ID 集合指标直接等同。Ragas 同时提供 Faithfulness、Response Relevancy 等生成评测指标。[Ragas 官方指标目录](https://docs.ragas.io/en/v0.4.1/concepts/metrics/available_metrics/)

### 2.2 生成：回答有没有依据、是否解决问题？

| 指标 | 检查内容 | 商城实例 |
| --- | --- | --- |
| 忠实性／Groundedness | 生成断言是否被提供的上下文支持 | 不能凭空说某书有十个实战项目 |
| 答案相关性 | 是否回应用户请求 | 问入门选书，回答不能只解释 Java 概念 |
| 答案正确性 | 是否符合可靠参考与实际事实 | 商品价格、适用难度是否正确 |
| 完整性 | 用户要求是否充分回应 | 预算、用途、难度是否都考虑 |
| 引用准确性 | 引用是否支持对应结论 | 原文存在，还要与推荐理由相关 |

忠实于过期资料仍可能事实错误，所以忠实性不能代替正确性。微软的评测文档同样区分检索过程与最终回答的 groundedness、relevance 等评估。[微软 RAG 评估器说明](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)

### 2.3 业务与运行指标

- 硬约束违规率：超预算、分类不符、下架、无可售库存的查询数／全部查询数；如按商品计数需另标分母。
- 商品事实错误率：不存在的 ID、错误价格／规格；由当前 MySQL 和返回内容核验。
- 无匹配表现：分别统计真正无匹配时的正确拒绝、明明有匹配时的错误拒绝；不能只看总体拒绝率。
- 索引新鲜度：商品提交至索引可检索的延迟；删除、下架、重试也需覆盖。
- 延迟 P50/P95/P99、错误／超时／降级率、吞吐、单次 token／费用：标明负载、样本量与模型版本。
- 线上点击、加购、转化、反馈用于业务观察；价格、促销和界面也有影响，需合理 A/B 对照才能归因于检索改进。

## 3. 如何组织测试

### 三种判断方法

| 方法 | 适合场景 | 如何控制误判 |
| --- | --- | --- |
| 固定标签＋程序评分 | 商品 ID 命中、排名、预算、库存等 | 校验标签与数据库快照；预测不能漏题或丢弃未知 ID |
| 人工评审 | 难度、用途、主观偏好、解释实用性 | 统一评分标准；关键样本交叉复核分歧 |
| LLM-as-a-Judge | 批量评估语义相关性、依据和完整性 | 固定评分提示与模型版本；用人工样本校准；不能把模型意见当绝对事实 |

能精确验证的库存、金额、ID 直接用程序核验。LLM judge 可辅助但有偏差，尤其生成和评分采用同一模型时需注意偏好。当前项目没有接入 Ragas 或 LLM judge，没有此类评分成绩。

### 实验流程

1. 从业务问题构建题集，覆盖正常、边界、困难负例、无匹配、表达变体；由独立人员复核标签。
2. 分开开发集和未参与调参的验收集。根据验收集反馈改动后，应另建新验收题。
3. 冻结商品快照、题集、模型、提示词、topK、阈值和代码版本；比较 keyword、vector、hybrid 时每次只改变待比较因素。
4. 分别做组件评测和端到端评测：前者提交明确约束定位检索问题；后者只提交用户语言，评估约束理解、召回、生成及最终事实。
5. 保存原始响应和逐题判断，报告分子／分母与失败案例；不删除超时、降级、无匹配等不利样本。随机生成测试重复运行并报告波动。
6. 完成质量对照后，再用明确负载做性能测试；离线效果好不能直接推导线上转化或高并发能力。

## 4. 本项目的方法和实际数据

方法：固定合成数据＋预先标注＋真实 MySQL/统一 ProductRetrievalService 关键词输出＋Python 确定性评分。工程测试另外验证事务、索引、消息重试、鉴权和降级。不是让模型自行生成答案再自行给自己打分。

输入：100 件合成图书、50 条问题（dev 30、heldout 20）。包含相关商品、禁止商品、预算、分类、库存标签。原始排序预测来自已执行实验，本次离线重新计算，不是新模型调用。

| 指标 | 开发集 | 保留集 |
| --- | ---: | ---: |
| Hit@5（仅有匹配题） | 29/29 = 100% | 18/19 = 94.74% |
| 标注 Precision@5 | 0.2138 | 0.1895 |
| 标注 Recall@5 | 1.0000 | 0.9474 |
| 出现禁止商品的问题数 | 11/30 | 2/20 |
| 硬约束违规问题数 | 0/30 | 0/20 |
| 无匹配题正确返回空 | 1/1 | 1/1 |
| 项目查询验收通过 | 19/30 = 63.33% | 17/20 = 85% |

查询验收要求：前五条覆盖全部相关标签（无匹配题返回空），且整个结果列表没有禁止商品、未知 ID 或硬约束违规。此指标不意味着所有未标注候选都被证明合理。

Hit 按有匹配题统计；Precision/Recall 先逐题计算，再对有匹配题宏平均。每题标签较少且不穷尽，P@5 不能直接解释为用户满意度或业务准确率。合并通过数是 36/50，不能拿 47/48 的命中数宣称整体推荐效果接近 98%。MRR/NDCG 和真实生成质量当前未报告。

局限：标签尚未经独立人工复核；science 占商品的 48%；题目存在相近变体；保留集已用于问题分析；只有两条无匹配题。collector 直接提交标签中的结构化 constraints，不能证明完整自然语言理解。固定测试向量不能证明语义召回。

复算（仓库根目录，Windows 可将 python3 改为 python）：

```sh
python3 infra/rag/fixtures/evaluate.py --predictions docs/测试/结果/rag/keyword-dev.json --split dev --k 5
python3 infra/rag/fixtures/evaluate.py --predictions docs/测试/结果/rag/keyword-heldout.json --split heldout --k 5
```

Hit 和查询通过数的复算脚本、历史集成测试证据见 [RAG 验证记录](RAG验证记录.md)；数据准备和采集见 [RAG 测试数据与评测](RAG测试数据与评测.md)。

## 5. 接入真实模型需要什么？

根据当前代码，需要两类模型能力：

| 能力 | 当前实现 | 所需配置 |
| --- | --- | --- |
| 商品与查询向量化 | DashScope Embedding SDK | DASHSCOPE_API_KEY；EMBEDDING_MODEL 默认 text-embedding-v4；EMBEDDING_DIMENSIONS 默认 1024 |
| 根据候选选品与生成引用 | DeepSeekServiceImpl 直接 HTTP 调用 | OPENAI_API_KEY，实际应填写 DeepSeek key |

当前服务已读取 OPENAI_BASE_URL 和 OPENAI_MODEL（外部 properties 分别对应 spring.ai.openai.base-url 与 spring.ai.openai.chat.options.model）；本次设置为 DeepSeek 官方地址及 deepseek-v4-flash。其他提供商仍需验证接口兼容性。

把凭据放在本机环境变量或 Git 忽略的运行配置，不需要在聊天或 Markdown 中发送真实 key。使用外部配置文件时检查配置优先级，避免文件中的占位值覆盖环境配置。告诉协作者提供商、模型、配置位置、额度／测试预算即可，不打印密钥。

- 仅有 Embedding：可做真实向量／混合检索对照，生成层仍未验证。
- 仅有生成 LLM：可测试“关键词召回＋LLM 选品”的生成链路；真实向量质量仍缺失。
- 两者都有：可进行当前完整链路评测。
- judge 模型是可选项，初期可用程序和人工评审，不必先配置第三个模型。

后续顺序：最小连通性检查 → 独立评测向量库构建与状态检查 → 50 题三策略对照 → 自然语言生成层采集与人工复核 → 新独立验收集。现有 collect_results.py 只收集 search 结果；完整生成评测还需要补充 recommend/chat 的原始响应采集与评分记录，不能只提供 key 就宣称已经测完。

真实 API 可能计费；本轮没有发起付费模型测试。模型／维度改变时建立独立索引并重新构建，不能复用固定 3 维测试索引或不兼容的历史向量。
