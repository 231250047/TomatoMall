# 测试方法与可信度

本文解释本次订单改造怎样验证，以及验证结论能覆盖到哪里。执行时间和输出见 [订单验证记录](订单验证记录.md)。本文整理历史结果，没有因为更新文档重新执行构建。

## 1. 先确定业务规则，再设计断言

测试的预期来自业务规则：可售库存不能为负；下单失败不能遗留部分预占；同一请求只能生成一张订单；一张订单只能发生一次终态库存变化；支付结果未知时不能贸然释放库存。

因此，检查内容包括数据库最终状态、库存数值、购物车和 Outbox，而不仅是返回值或日志。以下是实际用例：

| 场景 | 操作 | 关键断言 |
| --- | --- | --- |
| 多商品下单回滚 | 第一件库存足够，第二件不足 | 第一件 frozen 回到 0，订单数量不增加 |
| 数据库写入失败 | 订单金额超出字段精度，触发数据库异常 | 预占回滚，购物车仍在，Outbox 数量不增加 |
| 重复支付 | 库存 10，订单 A 预占 2、B 预占 3，A 支付两次 | amount=8、frozen=3，B 的预占仍在 |
| 并发抢库存 | 12 个用户同时购买库存为 5 的商品，每人 1 件 | 成功数为 5，frozen=5 |
| 支付与超时竞争 | 两个线程分别执行支付和超时处理 | frozen=0；SUCCESS 时 amount=3，TIMEOUT 时 amount=5 |
| 发送确认不确定 | 模拟发送后抛异常，再重试 | 使用同一 eventId、同一截止时间，成功后不再投递 |

业务字段含义：`amount` 是尚未售出的库存总量，`frozen` 是待支付预占，可售量为两者之差。

## 2. 分层验证：哪些真实执行，哪些使用替身

| 层次 | 实际执行 | 使用替身或限制 |
| --- | --- | --- |
| 单元和控制器测试 | 金额校验、缓存降级、直接调用控制器、使用本地 RSA 密钥和支付宝 SDK 验签 | Repository、Redis 或服务依赖按用例模拟；不经过完整 HTTP 链路 |
| H2 事务集成测试 | Spring 服务、事务代理、JPA、SQL 和数据库最终状态 | 支付网关、缓存、消息发布器模拟 |
| MySQL 事务集成测试 | 同一套 19 个事务用例改用独立 MySQL 8.0.46，验证实际数据库锁和回滚 | 外部支付、缓存和消息发布器仍模拟 |
| RocketMQ 集成测试 | 真实 Broker、SDK、网络投递、延迟消费、重复处理和 Broker 强杀后恢复 | 数据库使用 H2；缓存与支付网关模拟，使用未发起支付订单 |
| 构建与迁移检查 | Java 干净构建、前端打包、临时数据库迁移保护与结构检查 | 前端未做浏览器业务端到端；迁移未使用用户存量数据 |

默认测试共 26 个：事务 19、控制器 4、缓存 2、金额回归 1。MySQL 的 19 个是重复验证这组事务用例，不能宣称为另外 19 个独立场景。RocketMQ 测试需要显式执行。

这几层没有组成“真实 MySQL + Redis + MQ + 支付宝”的完整端到端环境。

## 3. 怎样减少测试自身带来的误判

### 3.1 确认测试能够发现旧问题

修复前实际执行的三个回归检查分别暴露了金额未校验、数据库未预占库存、多商品缺货未正确失败的问题；修复后重新执行通过。这说明这些断言能够识别对应缺陷。并非全部 26 个测试都经历了修复前失败的过程。

### 3.2 让业务事务真正提交和回滚

`OrderTransactionTest` 使用 `@Transactional(propagation=Propagation.NOT_SUPPORTED)`，不让测试方法自身包住整个业务调用。业务服务经 Spring 代理执行自己的事务，调用结束后再查数据库验证结果。

同时使用 `@AutoConfigureTestDatabase(replace=NONE)`，根据参数选择 H2 或 MySQL，避免指定 MySQL 后被测试框架替换成内存数据库。服务、Repository 和关键库存 SQL 都真实运行。

测试使用独立数据库和测试账号；每个用例创建独立用户、商品等数据，部分断言比较执行前后的数量。并非每个用例都独享一套新数据库，后续扩展跨订单扫描用例时仍需注意数据隔离。

### 3.3 用并发入口和最终状态一起判断

并发测试用线程池和 `CountDownLatch` 统一放行，让请求尽量同时进入业务方法，再等待所有 Future 完成并检查库存和状态。线程执行超时或非预期异常会使测试失败。

这能发现本次执行中的并发错误，但无法遍历线程调度的所有组合，也没有给出 QPS 或容量结论。支付与超时竞争用例验证本地状态竞争，不等于真实支付渠道竞争已验证。

### 3.4 排除“其实是兜底任务关了订单”的假阳性

真实 RocketMQ 测试没有启动数据库超时扫描。正常测试将订单和消息截止时间设为约 8 秒后，重启测试设为约 45 秒后，加快验证；业务配置仍是 30 分钟。

重启实验在实际发送成功、Outbox 已标记发送且订单仍待支付后，强杀独立 Broker，再用相同存储目录启动。随后观察消息触发关单；重复发送相同事件，并用 Spy 确认真实 Handler 至少执行两次，最终库存只释放一次。

因此它支持“该本地 Broker 进程重启后消息恢复、重复处理不重复释放”的结论，不支持磁盘损坏、多副本容灾或任意故障不丢消息的结论。

### 3.5 区分故障注入和真实故障

- Redis 不可用：让模拟对象抛异常，验证业务降级和重试分支；未强杀真实 Redis。
- 发送确认丢失：模拟发布器记录发送后抛异常；未实际丢弃网络确认包。
- Outbox 租约过期：构造过期租约状态；未强杀发布进程。
- Broker 重启：确实执行了进程 SIGKILL 和重新启动。
- 支付结果未知、已支付、已关闭：模拟渠道返回值；未完成支付宝沙箱交易。

## 4. 如何复现

环境准备和完整命令见 [01-普通订单与超时消息实现](../实现/普通订单与超时消息.md)。在后端目录、Java 17 环境下，核心入口为：

```sh
mvn -B -ntp clean verify
mvn -B -ntp -Dtest=OrderTransactionTest '-Dorders.test.jdbc-url=jdbc:mysql://127.0.0.1:33077/tomatomall_order_test?serverTimezone=UTC' -Dorders.test.db-user=root test
mvn -B -ntp -Dtest=RocketMqTimeoutIT -Dorders.test.mq-endpoints=localhost:18081 test
```

MySQL 用例配置 `create-drop`，只能连接可销毁的独立测试库。MySQL、MQ 命令要求事先准备对应服务；重启实验还需要按验证记录执行标记等待、强杀与重启步骤，单独运行 MQ 命令不会自动强杀 Broker。

代码入口：[事务用例](../../tomatoMall-backend/src/test/java/com/example/tomatomall/service/serviceImpl/OrderTransactionTest.java)、[真实 MQ 用例](../../tomatoMall-backend/src/test/java/com/example/tomatomall/service/serviceImpl/RocketMqTimeoutIT.java)、[控制器用例](../../tomatoMall-backend/src/test/java/com/example/tomatomall/TomatoMallApplicationTests.java)。

## 5. 还不能保证什么

测试增加可信度，不构成完整正确性证明。实现者编写的测试也可能重复实现者的误解；目前没有变异测试、完整覆盖率报告、容量压测或全部并发时序证明。已有独立静态审查也不能替代运行验证。

后续按风险补充：

1. 在真实 MySQL、Redis、MQ 组合环境中跑下单到关单全链路，再接支付宝沙箱。
2. 用同步屏障固定关键竞争点，增加多轮并发、数据库死锁重试和服务重启场景。
3. 收紧部分仅断言 `RuntimeException` 的用例，同时检查明确错误原因和全部业务状态。
4. 验证浏览器完整购买流程、真实历史数据迁移；上线前另做容量、积压和恢复时间测量。

## 6. 面试中怎样回答“你怎么证明实现可靠”

可以这样回答：

> 我从库存不超卖、事务整体回滚、订单终态幂等这些业务规则设计测试。关键服务和数据库操作真实执行，19 个事务用例既在 H2 运行，也在独立 MySQL 重跑。并发用例让 12 个用户抢 5 件库存，检查成功数和最终预占；MQ 用例实际强杀 Broker 并重启，关闭数据库兜底扫描以确认消息确实被消费。支付和 Redis 故障目前主要通过替身注入，所以我会把这些结果与真实支付端到端、生产容灾区分开说明。

追问“全通过就没问题了吗”：不能。还要结合事务设计、状态机、代码审查和上线后的监控对账；测试结论必须限定在执行过的场景和环境内。
